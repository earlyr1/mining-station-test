# Виртуальные очереди

По телеметрии машин сервис на Python восстанавливает очереди к четырём станциям, держит прогноз на 30 минут вперёд
и рекомендует машине другую станцию, если там её примут заметно раньше. Он читает `telemetry.v1` из Kafka (брокер —
Redpanda), публикует `queue.v1` и `decision.v1`, а состояние и offset хранит в Postgres одной транзакцией. Рядом —
генератор телеметрии, исполняющий рекомендации, сквозные проверки с авариями и витрина.

Ответы на 7 вопросов об архитектуре — в [ARCHITECTURE.md](ARCHITECTURE.md), задание — в [docs/TASK.md](docs/TASK.md),
полный дизайн — в [спецификации](docs/superpowers/specs/2026-10-13-virtual-queues-design.md).

## Быстрый старт

Нужны Docker с Docker Compose (команда `docker compose`; проверено на v5.5.1, ранние v2 не знают флагов Makefile
`up --wait-timeout` и `--profile '*'`) и GNU Make (проверено на 3.81). Для тестов, `make lint` и сквозных прогонов —
ещё [uv](https://docs.astral.sh/uv/): Python 3.13 он поставит сам по `.python-version`.

```sh
make up               # стенд с демо-генератором в реальном темпе; ждёт готовности и печатает адреса
VQ_SPEED=20 make up   # то же с ускорением ×20: в реальном темпе цикл машины длится около 40 минут
make logs             # логи всех сервисов
make down             # остановить стенд; тома Redpanda и Postgres сохраняются
make reset            # удалить оба тома и поднять стенд заново
```

`make up` возвращается, когда `dispatcher` получил партицию: при собранном образе — примерно через 17 с, первый
запуск ещё собирает образ. Порты публикуются только на `127.0.0.1`; номер меняется переменной в окружении или в
`.env` (в репозиторий он не входит). Умолчания:

| Что | Адрес | Переменная |
|---|---|---|
| Витрина | http://localhost:8000 | `VQ_VIEWER_PORT` |
| Redpanda Console | http://localhost:8080 | `VQ_CONSOLE_PORT` |
| Grafana, дашборд | http://localhost:3000/d/vq | `VQ_GRAFANA_PORT` |
| Prometheus | http://localhost:9090 | `VQ_PROM_PORT` |
| Kafka API для процессов на хосте | `127.0.0.1:19092` | `VQ_KAFKA_PORT` |
| Admin API Redpanda | `127.0.0.1:19644` | `VQ_ADMIN_PORT` |
| Postgres (пользователь, пароль и база — `vq`) | `127.0.0.1:5432` | `VQ_PG_PORT` |
| `/metrics` dispatcher и генератора | `127.0.0.1:9100`, `127.0.0.1:9101` | `VQ_DISPATCHER_METRICS_PORT`, `VQ_GENERATOR_METRICS_PORT` |

- `make up UP_PROFILES=` — стенд без демо-генератора.
- Демо-генератор запущен с `--allow-dirty`: после `make down` повторный `make up` продолжает по непустому топику, и
  модель сходится примерно за цикл. Чистый прогон — `make reset`.
- `config/site.toml` (его генерирует `tools/make_site.py`) копируется в образ: правку применяет `make up`, а при
  сохранённом состоянии — только `make reset`. Иначе `dispatcher` отказывается стартовать, и `make up` печатает
  причину (`start_refused`).
- Перехват standby: `docker compose --profile standby up -d dispatcher-b`, затем `docker compose stop dispatcher` —
  через 10,6–12,3 с партицию забирает `dispatcher-b`; после `docker compose start dispatcher` она возвращается.
- `make e2e` и `make e2e-chaos` начинают с `make reset` — тома стираются.

Без make — то же, что `make up`:

```sh
mkdir -p out && VQ_UID=$(id -u) VQ_GID=$(id -g) docker compose --profile demo up -d --build --wait
```

`VQ_UID`/`VQ_GID` — пользователь хоста для сервисов приложения: без них на Linux генератор не может писать в `./out`
и не стартует. Остановка — `docker compose --profile '*' down --remove-orphans`; с `-v` удаляются и тома, как в
`make reset`.

## Тесты

| Команда | Что проверяет | Последний прогон |
|---|---|---|
| `make test` | правила ТЗ и всё, что проверяется без брокера и БД | 757 тестов, ~53 с |
| `make test-integration` | хранилище на настоящем Postgres (testcontainers, нужен Docker) | 18 тестов, ~5,5 с |
| `make e2e` | сквозной прогон на стенде с нуля, затем `verify` | PASS, 3,5–4 мин |
| `make e2e-chaos` | то же плюс две аварии `dispatcher` | PASS, 3,5–4 мин |
| `make verify` | сверка лога с офлайн-прогоном ядра на поднятом стенде | 0 расхождений, ~17 с |
| `make bench` | время расчёта на сообщение, стенд не нужен | 73 мкс на сообщение, ~45 с |
| `make lint` | `ruff check` и `ruff format --check` по всему репозиторию, `mypy --strict` по `src` и `tools` | без замечаний |

**`make test`** = `uv run pytest -m "not integration"`. Правила ТЗ проверяются без брокера: занятие и освобождение
станции (`test_occupation.py`), очередь (`test_queue.py`), выбор станции (`test_decision.py`), порядок, дубли и
невалидный вход (`test_ordering.py`), публикация (`test_publication.py`), пример ТЗ байт в байт (`test_example.py`).
Сверх правил: детерминизм и рестарт из сохранённого состояния в любой точке потока (`test_determinism.py`);
замкнутый контур «симулятор → сбои → ядро → решения обратно» — по 2 ч симуляции с задержкой решений 0, 6 и 200 с,
на каждом тике станцию у симулятора и у ядра занимает одна и та же машина (`test_closed_loop.py`); генератор,
`dispatcher`, витрина и `vq-verify` на подделках Kafka и Postgres; compose и Makefile (`test_infra.py`).
Property-тесты (hypothesis) проверяют, что ядро не бросает исключений ни на каком входе. В конце pytest печатает
секцию «цифры прогона»: точность прогноза и наименьший зазор позиций генератора до порогов ядра (радиусы 50 м и
1500 м, точка округления ETA) — запас на случай, если на другой платформе гаверсинус разойдётся в последнем бите.
Часть `test_infra.py` требует docker CLI (демон не нужен), `make` и `bash`, тесты страницы витрины — `node`; без них
эти тесты пропускаются.

**`make test-integration`** — `test_store_pg.py` на `postgres:18.4-trixie`: миграция и сверка схемы, `claim` и
фенсинг чекпоинта по `epoch`, побитовое сохранение и чтение состояния, рестарт из Postgres без потерь и повторов,
отказы старта (другие версии, чужое состояние, другая схема), замёрзший сервер (`docker pause`) — выход за срок
сторожа.

**`make e2e`** — `make reset` без демо-генератора, генератор `--speed 20 --duration 3600 --seed 42` (час симуляции),
ожидание, пока `dispatcher` догонит лог, и `vq-verify` в образе приложения. Каждая из 11 проверок печатается строкой
PASS/FAIL, итог — в `out/e2e.json`. Последний прогон: отправлено 144 723 сообщения (723 дубля, 211 опозданий,
41 обрыв связи); отброшено 934 — ровно столько, сколько ожидал генератор; решений 32 `recommended`, 32 `no_gain`,
0 `stale_telemetry`, все рекомендации исполнены до начала обслуживания, самолечений 0; `verify` — 651 запись
`queue.v1` и 64 `decision.v1` совпали с офлайн-прогоном, расхождений 0. Счётчики от прогона к прогону немного
разные: решения возвращаются в генератор через Kafka с настоящей задержкой, поэтому проверки — равенства, а не
константы.

**`make e2e-chaos`** — то же плюс две аварии `dispatcher`, пока генератор пишет: на 25 % прогона точка аварии
`VQ_CRASH_FILE` (процесс выходит с кодом 137 после отправки пачки с записями и до её чекпоинта, поэтому повтор
детерминирован), на 55–65 % — `kill -KILL -1` изнутри контейнера. Проверяются код 137, перезапуск политикой Docker,
новый `claim` и чекпоинт, рост `epoch` и повторы в `verify` — байт в байт; итог — в `out/e2e-chaos.json`. Время от
выхода процесса по часам ВМ Docker, все прогоны (обе аварии дают одинаковые числа, разброс — от нагрузки машины):

| Событие | Время |
|---|---|
| старт контейнера политикой `restart: unless-stopped` | 0,12–0,33 с |
| `claim`: партиция получена, состояние прочитано из Postgres | 0,66–1,14 с |
| первый чекпоинт | 0,70–1,21 с |

После точки аварии её пачка уходит повторно — 1–3 записи `queue.v1`, все байт в байт; после `kill` повторов в
прогонах не было.

Вручную на демо-стенде: standby после штатной остановки активного забирает партицию через 10,6–12,3 с
(`session.timeout.ms` 10 с: static-участник не шлёт LeaveGroup); перезапущенный контейнер получает её сразу.

**`make verify`** — `vq-verify` в образе приложения: берёт N = `processor.next_offset`, прогоняет
`telemetry.v1[0, N)` через ядро офлайн с пустого состояния и сверяет `queue.v1` и `decision.v1` по ключам и
`vq-src-offset`. Повторы обязаны совпасть байт в байт, точные счётчики Postgres — с офлайн-счётчиками, инварианты
проверяются после каждого сообщения. Код 0 — совпало; последняя строка вывода — JSON.

**`make bench`** — `vq-bench` в образе приложения: час телеметрии замкнутого контура (144 723 сообщения, seed 42),
три прохода ядра. 73 мкс на сообщение (Linux aarch64, Python 3.13.15), хэш выходов одинаков во всех проходах. При
40 сообщениях/с это ≈ 0,3 % одного CPU-ядра; 400 машин — ≈ 600 мкс на сообщение и ≈ 24 % ядра (разовый замер на
хосте; в `make bench` число машин не меняется); одно ядро насыщается примерно на 700–800 машинах на площадку.

## Что сделано

- **Сервис `vq-dispatcher`** (`src/vq/dispatcher`) — процессор с консьюмер-группой `dispatcher`. Читает
  `telemetry.v1` пачками до 500 сообщений, прогоняет их через ядро по одному, отправляет `queue.v1` и `decision.v1`
  с заголовком `vq-src-offset` (offset породившего сообщения), затем одной транзакцией пишет в Postgres состояние и
  offset при условии `epoch = мой` (`migrations/001_state.sql`). Crash-only: сбой — `exit(1)` и рестарт с последнего
  чекпоинта, отказ старта — `exit(2)` с причиной и подсказкой `make reset`. Static membership и standby
  `dispatcher-b`, сторож Postgres, JSON-логи; каждое решение логируется с ETA и ожиданием по всем станциям.
- **Ядро** (`src/vq/core`) — правила ТЗ как детерминированный шаг «состояние + сообщение → новое состояние, выходы
  и события»: без I/O, часов и случайности, «сейчас» — только из `ts`. Пример ТЗ воспроизводится байт в байт;
  спорные места — в «Трактовках ТЗ».
- **Конфигурация** (`config/site.toml`, генерирует `tools/make_site.py`) — площадка `site-1`: 4 станции в 10 км от
  разгрузки, 40 машин (13, 11, 9 и 7 на станцию), константы ТЗ в `[constants]`; при загрузке проверяются геометрия,
  закрепление и типы.
- **Генератор `vq-generator`** (`src/vq/generator`) — машины едут по прямой (дуге большого круга) со скоростью
  10 м/с, обслуживаются 200 с и 30 с маневрируют, у занятой станции ждут в порядке приезда; рекомендации из
  `decision.v1` исполняются. Реальный темп или ускорение (`--speed N`), дубли, опоздания до 60 с и обрывы связи по
  seed; генератор считает, сколько сообщений сервис обязан отбросить. Итог прогона — `out/summary.json`.
- **Проверки** — `vq-verify`, `tools/e2e.py` (`make e2e`, `make e2e-chaos`) и `vq-bench`, числа — выше. Сбои
  Postgres проверены вручную на стенде, скриптов для них в репозитории нет: заморозку ловит сторож (выход через
  ~15 с), обрыв сети — `tcp_user_timeout` (выход через ~10 с), а при остановке Postgres новый процесс ждёт его на
  старте и делает `claim` через 0,85 с после возврата; после прогона со всеми тремя сбоями `vq-verify` — без
  расхождений. Выход при заморозке проверяет и `make test-integration`.
- **Витрина `vq-viewer`** (`src/vq/viewer`: FastAPI и страница на чистом JS и SVG) — карта, очереди, решения и
  здоровье конвейера; см. «Как читать витрину».
- **Метрики и Grafana** — `/metrics` у `dispatcher` и генератора, Prometheus и дашборд «Виртуальные очереди»
  (`/d/vq`, генерирует `tools/gen_dashboard.py`): состояние, поток и отбросы против ожидания генератора, решения и
  исполнение рекомендаций, точность прогноза, очереди станций, чекпоинт и лаг.
- **Redpanda Console** — сообщения топиков и лаг группы `dispatcher`.

### Точность прогноза

Прогноз — начало обслуживания, предсказанное при решении; ошибка — фактическое занятие минус прогноз. ТЗ порога не
задаёт. Критерий (`test_closed_loop.py::test_prediction_accuracy`): занятие спокойное, если предшественники у
станции те же, что в момент решения; каждое спокойное занятие обязано уложиться в 0 ≤ ошибка ≤ 2 + 2·L (1–2 с —
округление ETA и тик остановки, L — на сколько тиков запоздал поворот), у каждого возмущённого должна быть названа
причина; доля занятий с ошибкой в пределах ±5 с — только порог регрессии.

| Замкнутый контур, 2 ч, seed 42 | Ошибка в пределах ±5 с, все занятия | Спокойные занятия |
|---|---|---|
| решения без задержки | 109 из 118 (92,4 %) | 107 из 107, ошибка 0–2 с |
| задержка решений 6 с | 100 из 119 (84,0 %) | 100 из 104 в пределах ±5 с, все в границе 2 + 2·L |

На 8 seed (1, 3, 5, 7, 11, 13, 42 и 2026), с задержкой 6 с и без, в пределах ±5 с — 84–92 % всех занятий и
96–100 % спокойных. Наша исходная цель — 95 % занятий в пределах ±5 с — по правилу ТЗ недостижима: правило
считает ожидание только для решающей машины, поэтому поздняя рекомендация на соседнюю станцию (≈ 220 с пути)
обгоняет раннюю рекомендацию на дальнюю (350–500 с пути), и прогноз ранней сдвигается на целое занятие — 230 с.

## Как читать витрину

Витрина (http://localhost:8000) обновляется дважды в секунду и показывает модель сервиса, а не «истину» генератора.

- **Шапка.** «Сейчас» — время событий процессора (наибольший учтённый `ts`), а не часы компьютера. Справа —
  источники: Kafka, Postgres, dispatcher, генератор; недоступный помечается, остальное продолжает обновляться.
- **Полоса здоровья.** «Телеметрия» — точные счётчики из Postgres: принято, отброшено, ожидалось (по генератору),
  невалидно; метка «совпадает» — отброшено ровно столько, сколько ожидал генератор. «Решения» и «Прогноз» (доля
  занятий с ошибкой прогноза в пределах 5 с) — счётчики процесса `dispatcher` с его запуска. «Процессор» — `epoch`,
  `next_offset`, возраст чекпоинта, лаг и самолечение (при послушном генераторе 0).
- **Карта.** Станции с кругами 50 м и 1500 м, разгрузка, машины цветом фазы: к станции, ждёт, обслуживание,
  выезжает, к разгрузке. Пунктир к цели — машина перенаправлена, бледная точка — нет свежей позиции.
- **Отметки над картой:** «очереди — последнее изменение на offset X, карта на offset Y». X — offset сообщения
  `telemetry.v1`, которое последним изменило какую-то очередь; `queue.v1` публикуется только при изменении, поэтому
  X < Y — норма. Y = `next_offset − 1` — срез Postgres, по которому нарисована карта. Если X > Y, добавляется
  «очереди впереди карты на N»: выходы пачки уже отправлены, а чекпоинт ещё нет (разрыв не больше пачки). После
  аварии появляется «повторов отброшено N».
- **Очереди станций** — из `queue.v1`, по станции берётся запись с наибольшим `vq-src-offset`. В шапке карточки —
  кто занимает станцию и до какого времени; строки — машина, приезд («—» у уже стоящей у станции), обслуживание
  (начало и освобождение), ожидание; «из S1» — машина перенаправлена со своей станции. Внизу — время и offset
  последнего изменения.
- **Решения** — последние записи `decision.v1` (до 120) без повторов по `(unit_uuid, at)` и итоги по всему логу.
- После `make down` → `make up` метки «совпадает» нет: счётчики процессора накопительные, а ожидание генератора —
  за его запуск; «Решения» и «Прогноз» считаются с перезапуска процесса.

## Трактовки ТЗ

Тип: **отступление** — делаем не как написано; **трактовка** — ТЗ молчит или неоднозначно; **наше** — добавлено
сверх ТЗ. Тесты лежат в `tests/`.

| № | Тема | Тип | Решение | Почему | Тест |
|---|---|---|---|---|---|
| 1 | Передача станции | отступление | В момент освобождения станция переходит к первой по приезду ждущей машине из свежих и стоящих; занятие — в момент освобождения, не раньше её приезда (п. 19) | По букве правила 1 станцию берёт тот, чьё сообщение первым пришло после освобождения, — порядок лога, а не приезда; правило очереди и генератор требуют FIFO | `test_occupation.py::test_release_by_timer_and_fifo_handover_at_release_moment`, `test_occupation.py::test_stale_and_moving_candidates_are_skipped_in_handover` |
| 2 | Повторное занятие | отступление | Освобождённая таймером и ещё стоящая в радиусе машина станцию снова не занимает и в очередях не стоит | Иначе по букве правила 1 она заняла бы станцию в ту же секунду, и таймер потерял бы смысл | `test_occupation.py::test_served_vehicle_does_not_reoccupy`, `test_queue.py::test_served_vehicle_not_in_any_queue` |
| 3 | Какая станция «на станции» | трактовка | Целевая: своя, после рекомендации — рекомендованная. Остановка «к станции» в радиусе другой станции — приезд к ней (самолечение): она становится целью, свободную станцию машина занимает, у занятой ждёт с приездом = вход в радиус; проезд на скорости только запоминает вход. ## Что сознательно не сделано и почему

- **Несколько площадок.** В ТЗ одна площадка; путь масштабирования (партиционер по площадке или этап-секвенсор) —
  в [ARCHITECTURE.md](ARCHITECTURE.md), ответ 4.
- **Транзакции Kafka** (exactly-once на выходе, фенсинг продюсера). Атомарность нужна только паре «состояние +
  offset» — она в одной транзакции Postgres; выходам достаточно идемпотентности. Альтернатива и когда на неё
  переходить — в ARCHITECTURE.md, ответ 5.
- **Apache Kafka в compose.** Сервис говорит только по Kafka-протоколу, Redpanda заменяема без изменений кода.
- **Schema Registry, авторизация, TLS, отказоустойчивый Postgres, миграции схемы, алерты** — вне рамок тестового
  стенда; смена схемы — `make reset`.
- **Синхронное ожидание генератором решения (lockstep).** Генератор изображает площадку, а площадка решений не ждёт:
  запаздывание поворота видно в метрике `vq_gen_decision_delay_sim_seconds`, контур рассчитан на ускорение до ×20 —
  на нём идёт `make e2e`.
- **Защиты от редких искажений входа и пересмотр задним числом:** спешащие часы машины, дрожание GPS у границы
  радиуса, опоздание на 230 с и больше, пересмотр уже применённых переходов, освобождение станции по фактическому
  выезду задержавшейся машины. ТЗ этого не требует (опоздание в нём — до 60 с), генератор таких данных не создаёт;
  поведение по букве ТЗ — в «Известных ограничениях», часть случаев закреплена тестами.
- **Инкрементальный пересчёт очередей.** При 40 машинах расчёт занимает ≈ 0,3 % CPU-ядра; понадобится примерно с
  700–800 машин на площадку.
- По плану срезов на случай нехватки времени (Grafana → Prometheus → `bench` → витрина) не срезано ничего.

## Известные ограничения

- **Задержка на станции.** Обслуживание дольше 230 с — станцию передают по таймеру, прогноз для следующих
  оптимистичен. Так требует ТЗ; это же защищает от потерянной телеметрии занявшей.
- **Часы машины спешат.** «Сейчас» уходит вперёд, остальные машины становятся несвежими; нужен watermark или
  карантин будущих `ts`.
- **Дрожание GPS у границы радиуса.** Пороги строгие, без гистерезиса: одна точка занявшей в 50 м и дальше — выход,
  станция переходит к ждущей.
- **Применённые переходы не пересматриваются.** Опоздавший выход занявшей после таймера меняет только её фазу.
- **Опоздание на 230 с и больше** может занять свободную станцию уже после таймеров шага; такое занятие переживает
  свой таймер до следующего учтённого сообщения. ТЗ ограничивает опоздание 60 с.
- **Холодный старт без состояния при непустом топике.** Первая позиция трактуется как «к станции»; машина, едущая к
  разгрузке, считается неверно до разгрузки, дальше модель верна.
- **Пропущенный радиус разгрузки.** Если ни одна точка не попала в радиус 50 м разгрузки, машина остаётся «к
  разгрузке» (буква ТЗ).
- **Неисполненная рекомендация.** Модель сходится сама (самолечение, конец заезда в радиусе разгрузки), а до того
  прогноз у рекомендованной станции пессимистичен; срабатывания видны в `vq_fsm_resync_total`.
- **Выигрыш считается по ожиданию, а не по началу обслуживания.** В примере T4 на S2 начнёт обслуживание на 70 с
  позже, чем на S1, но правило ТЗ рекомендует S2; сделано как в ТЗ.
- **Точность прогноза** — 84–92 % занятий в пределах ±5 с, а не 95 % (см. «Точность прогноза»).
- **Выходы at-least-once.** После падения возможны повторы, в том числе одинаковые очереди подряд и повтор решения;
  потребитель схлопывает их по `vq-src-offset` и `(unit_uuid, at)`.
- **Поздние записи зомби и компакция `queue.v1`.** Потребитель отбрасывает их по `vq-src-offset`, а компакция
  оставляет последнюю по позиции: если станция больше не публиковалась, текущей останется устаревшая очередь.
  Лечится следующей публикацией станции, полностью — фенсингом продюсера (транзакции Kafka).
- **Перепрогон на другой платформе.** Детерминизм гарантирован для тройки «код + `site.toml` + образ»: от версии
  Python и libm зависит последний бит гаверсинуса, поэтому `make verify` и `make bench` идут в образе приложения.
- **Брокер — одна нода Redpanda в режиме dev-container (RF=1, без fsync).** Потеря ноды — потеря данных; в
  продакшене RF=3, `acks=all`, `min.insync.replicas=2`.
- **Standby после штатной остановки** забирает партицию только через `session.timeout.ms` (10,6–12,3 с):
  static-участник не шлёт LeaveGroup.
- **Один `group.instance.id` у двух процессов** — они вытесняют друг друга по кругу; поэтому у standby свой id, а
  `dispatcher`, запущенный с хоста рядом со стендом, обязан задать свой `VQ_GROUP_INSTANCE_ID`.
- **Отказ старта в цикле.** Код 2 (`logic_version_changed`, `config_changed`, `schema_changed`,
  `state_older_than_log`, `log_recreated`, `partitions`) Docker повторяет с растущей паузой, пока не сделан
  `make reset`; причину показывают `make up` и `make logs`.
- **Схема без миграций.** Смена схемы таблиц, `logic_version` или `config_hash` (в том числе `[constants]`) требует
  `make reset`: состояние и лог удаляются вместе.
- **Перезапуск генератора без сброса** не поддерживается: на непустом топике он отказывается стартовать. Демо с
  `--allow-dirty` сходится примерно за цикл, но «отброшено = ожидалось» после такого рестарта не сходится.
- **Инкрементальности нет.** Все очереди пересчитываются на каждое сообщение; одна площадка — одна партиция — одно
  CPU-ядро, масштабирование — по площадкам.
