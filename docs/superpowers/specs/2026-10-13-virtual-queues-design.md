### 1.2 Решения, принятые вместе с кандидатом

1. Объём: всё, что требует задание, плюс витрина — живая страница, метрики Prometheus с дашбордом Grafana, Redpanda Console.
2. Брокер — Redpanda (Kafka API) в docker compose.
3. Генератор всегда выполняет рекомендации: читает `decision.v1` и меняет маршрут.
4. Один процессор на площадку; `telemetry.v1` из одной партиции.
5. Состояние процессора — в Postgres, нормальной моделью (`processor`, `stations`, `vehicles`), вместе с offset в одной транзакции; фенсинг по `epoch`. Транзакций Kafka и топика состояния нет; выходы идемпотентные, at-least-once.
6. Правила ядра — §3, включая перечисленные отступления от буквы ТЗ (§3.11).
7. Модель сама сходится с миром: машина «к станции», остановившаяся в радиусе любой станции, считается приехавшей к ней (цель становится этой станцией): свободную станцию она занимает по сообщению с остановкой, а у занятой её приезд, как у любой ждущей, — момент входа в радиус этой станции, а не остановки. Машина «к станции» в радиусе разгрузки заканчивает заезд, и на следующем подъезде решение снова возможно. Генератор исполняет рекомендацию, пока машина не начала обслуживание. Решения 14.10; первое заменяет прежнее «только целевая станция».
8. Python 3.13 и uv, docker compose, Makefile. `README.md` и `ARCHITECTURE.md` — на русском.
9. Если не успеваем, витрина режется раньше `verify`; `verify` и `e2e-chaos` не режутся (решение 14.10).
10. Apache Kafka в compose не добавляем: сервис говорит только по Kafka-протоколу, Redpanda заменяема; это строка в README и в таблице отступлений (решение 14.10).
11. Точность прогноза (решение 14.10, по итогам прототипа): исходная цель спеки «|ошибка| ≤ 5 с у 95 % занятий» (в ТЗ порога точности нет) по правилу ТЗ недостижима — ожидание считается только для решающей машины, и поздняя рекомендация на соседнюю станцию обгоняет раннюю дальнюю (на 8 seed — 84–92 % всех занятий). Критерий: каждое спокойное занятие — в узкой границе ошибки, у каждого возмущённого названа причина; общая доля печатается и держится порогом регрессии (§6.1).

## 2. Архитектура

### 2.1 Схема

```
 generator ──telemetry.v1 (1 партиция, key=unit_uuid)──▶ dispatcher ──queue.v1 (compact, key=station_uuid)──▶
     ▲                                                      │  │
     └──────────decision.v1 (key=unit_uuid)─────────────────┘  │ чекпоинт: состояние + offset при epoch = мой,
                                                               │ одна транзакция
                                                               ▼
 viewer :8000 ◀── queue.v1, decision.v1 ──      Postgres: processor / stations / vehicles
        ▲                                                      │
        └────────────── SELECT, только чтение ─────────────────┘

 dispatcher :9100/metrics (и standby dispatcher-b), generator :9101/metrics ──▶ Prometheus :9090 ──▶ Grafana :3000
 viewer ◀── /metrics dispatcher, dispatcher-b, generator (полоса здоровья, §5.1)
 Redpanda Console :8080
```

### 2.2 Сервисы docker compose

| Сервис | Образ | Роль | Порт на хосте (переменная) |
|---|---|---|---|
| `redpanda` | `docker.redpanda.com/redpandadata/redpanda:v26.2.3` | брокер, одна нода, `--mode dev-container --smp 1 --memory 1G` | 19092 (Kafka, `VQ_KAFKA_PORT`), 19644 (admin, `VQ_ADMIN_PORT`) |
| `redpanda-init` | тот же образ, `rpk` | одноразово: `auto_create_topics_enabled=false`, `group_initial_rebalance_delay=0`, создание топиков (§2.3) | — |
| `postgres` | `postgres:18.4-trixie` | состояние процессора | 5432 (`VQ_PG_PORT`) |
| `dispatcher` | образ проекта | процессор | 9100 (`VQ_DISPATCHER_METRICS_PORT`) |
| `dispatcher-b` | образ проекта | standby процессора, профиль `standby` — демо перехвата | — |
| `generator` | образ проекта | симулятор площадки, профиль `demo` (его поднимает `make up`) | 9101 (`VQ_GENERATOR_METRICS_PORT`) |
| `viewer` | образ проекта | живая страница | 8000 (`VQ_VIEWER_PORT`) |
| `console` | `docker.redpanda.com/redpandadata/console:v3.12.0` | просмотр топиков и лага | 8080 (`VQ_CONSOLE_PORT`) |
| `prometheus` | `prom/prometheus:v3.15.0` | сбор метрик | 9090 (`VQ_PROM_PORT`) |
| `grafana` | `grafana/grafana:13.2.2` | дашборд | 3000 (`VQ_GRAFANA_PORT`) |

- Порты публикуются только на `127.0.0.1`; номер на хосте переопределяется переменной из таблицы в окружении или в `.env` (`.env` в репозиторий не кладётся; умолчания — в таблице).
- Слушатели Redpanda: внутренний `redpanda:9092` для контейнеров, внешний `127.0.0.1:19092` для процессов на хосте (`tools/e2e.py`, отладка). Внешний адрес объявляется как `127.0.0.1`, а не `localhost`: порт опубликован только на IPv4, и librdkafka на хосте иначе сперва стучится в `[::1]` и пишет ошибки соединения.
- Порядок старта: `dispatcher`, `dispatcher-b` и `viewer` — после успешного `redpanda-init` и healthy `postgres`; `generator` — после `redpanda-init` (Postgres ему не нужен). У долгоживущих сервисов есть healthcheck, поэтому `up --wait` значит «готов»: `redpanda` — `rpk cluster health`; `postgres` — `pg_isready` по TCP (временный сервер initdb слушает только сокет и не должен считаться готовым); `dispatcher` — только после `claim`, по `vq_epoch > 0` в `/metrics` (сервер метрик поднимается раньше Kafka и `claim`, а при отказе старта `epoch` остаётся 0); `dispatcher-b` — ответ `/metrics` (пока активный жив, standby партицию не получает); остальные — ответ своего HTTP.
- `redpanda-init` (`deploy/redpanda-init.sh`) идемпотентен: выставляет и сверяет параметры кластера, создаёт только отсутствующие топики, затем сверяет число партиций, реплик и настройки (`rpk topic describe -s`, `-c`) и падает при расхождении — лечится `make reset`.
- `dispatcher` — `restart: unless-stopped`, `stop_grace_period: 10s` (crash-only, §2.4). Отказ старта (код 2, §2.4) Docker тоже перезапускает — в цикле с растущей паузой, пока не сделан `make reset`; `make up` тогда падает на healthcheck и печатает строку `start_refused` из лога `dispatcher` и подсказку про `make reset`. `site.toml` копируется в образ: `docker compose restart` правку не применяет, нужна пересборка (`make up`), а при сохранённом состоянии — ещё и `make reset`.
- Standby по умолчанию не запускается; для демо перехвата — `dispatcher-b` (профиль `standby`, те же `restart` и `stop_grace_period`) без проброса порта метрик и со своим `group.instance.id = dispatcher-site-1-standby` (переменная `VQ_GROUP_INSTANCE_ID`). Почему свой и почему он должен сортироваться после id активного — §2.4.
- `generator` — `restart: "no"`: перезапуск генератора без сброса не поддерживается (§4.4). Демо-генератор `make up` запускается с `--speed ${VQ_SPEED:-1} --allow-dirty`: `make down` сохраняет тома, и повторный `make up` идёт по непустому `telemetry.v1`. `make e2e` поднимает стенд без него и запускает свой генератор — `docker compose run --rm --use-aliases generator …` (без `--use-aliases` контейнер `run` не виден по имени `generator` ни Prometheus, ни витрине).
- Образ приложения один (`${COMPOSE_PROJECT_NAME:-vq}-app:latest`), собирает его только сервис `dispatcher`; у всех сервисов приложения `pull_policy: never`. Иначе каждый `up --build` пересоздавал бы все контейнеры приложения (тег достаётся последней сборке со своей меткой сервиса), а первый `make up` и `docker compose run` пытались бы скачать образ из реестра.
- Сервисы приложения работают от пользователя хоста (`user: ${VQ_UID}:${VQ_GID}`, Makefile берёт их из `id -u`/`id -g`, без него — 1000:1000): на Linux каталог `./out` принадлежит ему. У них `init: true`: PID 1 — tini, поэтому `kill -KILL -1` изнутри контейнера убивает процесс приложения, контейнер выходит с кодом 137, и `restart: unless-stopped` его поднимает. Так устроены аварии `make e2e-chaos` (§6.3): `docker compose kill` любым сигналом Docker считает ручной остановкой и контейнер не перезапускает.
- `restart: unless-stopped` — у всех долгоживущих сервисов, включая `redpanda` и `postgres`: после рестарта Docker поднимается весь стенд. У `redpanda-init` и `generator` — `"no"`.
- Тома: `redpanda-data` и `postgres-data`. Они живут и умирают вместе: `make down` их сохраняет, удаляет только `make reset` (§7). Хранилище Prometheus и каталог данных `redpanda-init` — tmpfs, поэтому `make down` не оставляет анонимных томов.

### 2.3 Топики

| Топик | Партиции | Ключ | Настройки | Назначение |
|---|---|---|---|---|
| `telemetry.v1` | 1 | `unit_uuid` | `cleanup.policy=delete`, `retention.ms=604800000` | вход; источник для перепрогона |
| `queue.v1` | 1 | `station_uuid` | `cleanup.policy=compact`, `min.compaction.lag.ms=86400000` | очередь станции; текущая очередь — запись с наибольшим `vq-src-offset`, а не последняя по позиции (поздние записи зомби, §2.6); история за сутки сохраняется для `make verify` |
| `decision.v1` | 1 | `unit_uuid` | `cleanup.policy=delete`, `retention.ms=604800000` | решения: команды генератору и аудит |

`dispatcher` при старте проверяет, что у `telemetry.v1` ровно одна партиция, и иначе отказывается работать (отказ старта `partitions`, §2.4; детерминизм, §2.7).

Каждая запись `queue.v1` и `decision.v1` несёт заголовок Kafka `vq-src-offset` — offset сообщения `telemetry.v1`, обработка которого её породила (десятичная строка). Запись и разбор заголовка — в ядре (`vq.core.codec`: `src_headers`, `parse_src_offset`), одни на `dispatcher`, `verify` и витрину; разбор признаёт только ASCII-цифры и не бросает исключений. Payload остаётся ровно по ТЗ; повторы после падения совпадают байт в байт вместе с заголовком. Пара `(station_uuid, vq-src-offset)` уникальна: шаг публикует не больше одной записи на станцию.

### 2.4 Процессор `dispatcher`

Один процесс, обработка в одном потоке; HTTP `/metrics` — в фоновом потоке `prometheus_client.start_http_server`, сторож Postgres — таймер (см. «Postgres»).

**Клиенты** (`confluent-kafka` 2.15.1):

- consumer: `group.id=dispatcher`, `group.instance.id=dispatcher-<site_id>` (static membership, ниже; переопределяется переменной `VQ_GROUP_INSTANCE_ID`, её задаёт только `dispatcher-b`), `session.timeout.ms=10000`, `heartbeat.interval.ms=3000`, `enable.auto.commit=false`, `auto.offset.reset=error`, `group.protocol=classic`, `partition.assignment.strategy=range`;
- producer: `enable.idempotence=true`, `acks=all`, `linger.ms=5`, `compression.type=zstd`, `message.timeout.ms=30000`;
- оба получают `error_cb` и `logger`: ошибки и логи librdkafka идут JSON-строками в общий лог.

**Группа и static membership** (проверено на Redpanda v26.2.3):

- перезапущенный контейнер с тем же `group.instance.id` получает партицию сразу, без ожидания таймаута (`claim` через 0,7–1,1 с после выхода процесса, §2.6);
- static-участник не шлёт LeaveGroup ни при аварии, ни при `consumer.close()` по SIGTERM (KIP-345; confluent-kafka не умеет его вынудить), поэтому участник с другим id — standby — получает партицию только через `session.timeout.ms`, в том числе после штатной остановки; вернувшийся активный забирает её обратно (`claim` через 0,6–3,5 с после старта контейнера);
- два процесса с одним id вытесняют друг друга по кругу: новый забирает партицию, старый получает `FENCED_INSTANCE_ID` или проваливает чекпоинт по `epoch` и выходит с кодом 1, Docker его перезапускает. Данные остаются верными, но `epoch` растёт, а пауза рестарта Docker доходит до 60 с. Поэтому у standby свой id, а запуск `dispatcher` с хоста рядом со стендом требует своего `VQ_GROUP_INSTANCE_ID`;
- range-ассайнер librdkafka упорядочивает static-участников по `group.instance.id` и отдаёт единственную партицию первому, поэтому id standby (`dispatcher-site-1-standby`) сортируется после id активного (`dispatcher-site-1`). Вход standby в группу — ребаланс: активный повторяет `claim` (`epoch` + 1, пауза до ~0,4 с).

**Старт:** конфигурация и `config_hash`; подключение к Postgres — недоступный ждём до 60 с (попытка раз в секунду, WARNING `waiting_for_postgres`), затем `exit(1)`; миграция и сверка схемы (§2.5); `/metrics`; клиенты Kafka; проверка одной партиции `telemetry.v1` (§2.3); подписка с колбэками ниже. Ожидание Postgres — внутри процесса: после быстрого выхода Docker удваивал бы паузу перед каждым рестартом (до 60 с), и после возврата Postgres площадка ждала бы очередного рестарта. В памяти ещё ничего нет, поэтому ожидание остаётся crash-only.

**Получение партиции** (`on_assign`, вызывается внутри `consume()`):

1. `store.claim(site_id)` — одна транзакция Postgres, строго в таком порядке: `INSERT INTO processor … ON CONFLICT DO NOTHING`; `UPDATE processor SET epoch = epoch + 1 WHERE site_id = … RETURNING epoch, next_offset, now_ts, logic_version, config_hash, счётчики`; проверка версий по `RETURNING` (§2.5; если состояния нет, версии просто переписываются); проверка, что в базе нет чужого состояния — строк `processor` другой площадки, а при пустом `next_offset` — строк `stations`/`vehicles` (иначе отказ `config_changed`); `SELECT` станций и машин с `ORDER BY` по ключу. Отказ откатывает транзакцию целиком: ни `epoch`, ни новая строка не остаются. Отдельного `SELECT processor` до `UPDATE` нет: строка блокируется `UPDATE`, поэтому параллельный `claim` и чекпоинт сериализуются.
2. Если `next_offset` задан, проверить `low ≤ next_offset ≤ high` по `get_watermark_offsets`. Иначе отказ старта (`state_older_than_log` или `log_recreated`) с подсказкой `make reset`; так же обрабатывается `ERR__AUTO_OFFSET_RESET`.
3. Собрать `Engine` из прочитанного состояния.
4. `assign` партиции с offset = `next_offset`, а если состояния ещё нет — явно low watermark (`get_watermark_offsets` без кеша, при каждом назначении). Это та же позиция, что `OFFSET_BEGINNING`, но процессор знает offset первой пачки, и проверка из «Потери партиции» работает с первой же пачки.

**Потеря партиции** (`on_revoke`, `on_lost`): выбросить `Engine` из памяти и не обрабатывать сообщения до следующего назначения. Сообщения, полученные до смены назначения, отбрасываются: перед применением первого сообщения пачки проверяется, что его offset равен ожидаемому (`next_offset` из `claim` или конец предыдущей пачки); иначе пачка отбрасывается и чтение переставляется на ожидаемый offset.

**Цикл:**

1. `consume(num_messages=500, timeout=0.25)`.
2. Каждое сообщение по одному: `engine.apply(value)` возвращает выходы и события.
3. Отправить выходы в порядке появления, с заголовком `vq-src-offset`, затем `flush(timeout=10)`. Если в очереди что-то осталось или пришла ошибка доставки — `exit(1)`.
4. Чекпоинт — одна SQL-инструкция в autocommit, то есть одна транзакция за один round-trip: `WITH p AS (UPDATE processor SET next_offset, now_ts, счётчики, updated_at WHERE site_id = … AND epoch = мой RETURNING 1)`, пакетный upsert 4 станций и до 40 машин (`INSERT … SELECT FROM unnest(...) WHERE EXISTS (SELECT FROM p) ON CONFLICT DO UPDATE`) и `SELECT count(*) FROM p`. Пустой `p` — партицию забрал другой экземпляр: не записано ничего, `exit(1)`. Соединение в autocommit, потому что иначе psycopg отдельно синхронизирует неявный `BEGIN`, и чекпоинт стоит три round-trip.
5. Обновить метрики по событиям пачки.
6. `consumer.commit(offset, asynchronous=True)` — только чтобы Console видела лаг группы `dispatcher`; `vq_consumer_lag_messages` — high watermark минус `next_offset`. Источник правды для offset — Postgres.

**Точка аварии** для `make e2e-chaos` (`VQ_CRASH_FILE`, в compose — `/tmp/vq-crash`; без переменной хук ничего не делает): если между шагами 3 и 4 пачки, отправившей хотя бы одну запись, файл существует — файл удаляется, пишется строка `chaos_crash` (`next_offset`, `records=N`), и процесс выходит с кодом 137, как от `kill -9`. Перезапуск повторяет пачку и детерминированно отправляет те же N записей ещё раз. Пачка без записей хук не вызывает (её повтор не дал бы ни одной повторной записи), и файл ждёт следующей пачки с записями.

**Ошибки — crash-only, но не на любую ошибку.** Коды выхода: 0 — SIGTERM (текущая пачка дописывается вместе с чекпоинтом); 1 — сбой, контейнер перезапускается; 2 — отказ старта, лечится `make reset` (`logic_version_changed`, `config_changed`, `schema_changed`, `state_older_than_log`, `log_recreated`, `partitions`), `restart: unless-stopped` повторяет его в цикле, пока не сделан сброс. `exit(1)` — при фатальной ошибке Kafka, ошибке доставки, фенсинге, любой ошибке Postgres или его молчании дольше срока сторожа, при исключении в ядре и при ошибке `site.toml` на старте (`ConfigError`, строка `exit_crash`; лечится исправлением файла и пересборкой, а не `make reset`). Фатальную ошибку consumer (например, `FENCED_INSTANCE_ID`) librdkafka отдаёт из `consume()` с кодом `_FATAL`, а confluent-kafka строит такой `KafkaError` с `fatal() == False`, поэтому проверяются и код, и флаг. Фатальную ошибку producer confluent-kafka 2.15.1 в `error_cb` не отдаёт, а бросает из вызова, который обслуживал клиента: `poll()` и `flush()` — `KafkaException` с `fatal() == True`, следующий `produce()` — с кодом `_FATAL`, а `flush()` при ожидающем `on_delivery` — `SystemError` с этой `KafkaException` в `__cause__`. Строка выхода ищет фатальную `KafkaException` в самом исключении и в цепочке его причин (`__cause__`, иначе `__context__`): нашла — `exit_kafka_fatal` с этой ошибкой в `error`. Информационные ошибки `consume()` (`_TRANSPORT`, `_ALL_BROKERS_DOWN`, `_PARTITION_EOF`) и прочие нефатальные только логируются: librdkafka переподключается сам. Перед выходом вызывается `consumer.close()` (LeaveGroup при этом не уходит, см. выше); сторож Postgres и точка аварии выходят через `os._exit` без него — состояние в Postgres атомарно, рестарт продолжает с последнего чекпоинта. Невалидное сообщение ошибкой не считается (§3.4), а ядро обязано не бросать исключений ни на каком входе (§6.1) — иначе одно сообщение остановило бы поток навсегда.

**Postgres:** соединение в autocommit с `connect_timeout=5`, `keepalives_idle=5`, `keepalives_interval=2`, `keepalives_count=3`, `tcp_user_timeout=10000` и `options='-c statement_timeout=5000 -c lock_timeout=2000 -c idle_in_transaction_session_timeout=10000'`. Серверные таймауты не срабатывают, если сервер заморожен или до него не доходят пакеты. Обрыв сети ловит `tcp_user_timeout`: данные без подтверждения дольше 10 с — ошибка соединения и `exit(1)`; без него запрос висел бы до исчерпания ретраев TCP (~15 мин). Замёрзший сервер ловит сторож процесса: миграция, `claim` и чекпоинт, не вернувшиеся за 15 с, — строка `exit_postgres_stalled` и `os._exit(1)`; иначе поток висел бы в запросе, heartbeat librdkafka держал бы партицию до `max.poll.interval.ms`, а `/metrics` отвечал бы. Чекпоинт, бывший в пути, замёрзший сервер может применить после разморозки — это безопасно: выходы его пачки уже отправлены, а после `claim` нового процесса его отвергнет фенсинг по `epoch`.

**Логи:** JSON-строка в stdout, формат общий для всех сервисов (`vq.logs`): `ts` (UTC, ISO 8601 с миллисекундами и `Z`), `level`, `logger`, `event`, затем `site`, `epoch`, `offset` и поля события, трассировка исключения — последним полем `error`; ошибки librdkafka — строкой `kafka_error`, её собственные логи — тоже JSON-строками (строка без полей события — `event: "log"`, текст в `msg`). INFO — `claim`, потеря партиции (`revoke`, `lost`) и каждое решение: ETA и ожидание по всем станциям — тот же расчёт ядра, по которому выбрана станция, — выбор, выигрыш. WARNING — `waiting_for_postgres`, отброшенная пачка (`batch_dropped`), нефатальные ошибки Kafka (информационные ошибки `consume()` — INFO). ERROR — фенсинг (`fenced`), отказ старта `start_refused` (причина и подсказка `make reset`, код 2), точка аварии `chaos_crash` и строки выхода с кодом 1: `exit_fenced`, `exit_delivery_failed`, `exit_postgres`, `exit_postgres_stalled`, `exit_kafka_fatal`, `exit_crash` (исключение, со стеком) — с причиной в поле `error` (у `exit_postgres_stalled` — `op` и `deadline_s`), `epoch` и offset начала упавшей пачки. `unit_uuid` — только в логах, не в метках метрик.

Порядок «сначала выходы, потом чекпоинт» гарантирует, что выходы не теряются: падение между `flush` и `COMMIT` приводит к повторной обработке пачки и повторной отправке тех же записей.

### 2.5 Состояние в Postgres

`migrations/001_state.sql`, применяется `dispatcher` при старте одной транзакцией под advisory-блокировкой (два экземпляра не применяют схему одновременно); в той же транзакции колонки таблиц сверяются с кодом (`stations` и `vehicles` — поля модели §3.3 и `updated_at`). Схема не мигрируется: `CREATE TABLE IF NOT EXISTS` существующую таблицу не меняет, поэтому том от другой схемы — отказ старта `schema_changed` (код 2, подсказка `make reset`), а не ошибка на первом `claim` и цикл рестартов. Каталог миграций переопределяется переменной `VQ_MIGRATIONS`.

```sql
CREATE TABLE IF NOT EXISTS processor (
  site_id        text PRIMARY KEY,
  epoch          bigint NOT NULL,
  next_offset    bigint,                -- NULL: ещё ничего не обработано
  now_ts         bigint,                -- «сейчас», секунды epoch
  logic_version  text   NOT NULL,
  config_hash    text   NOT NULL,
  msgs_accepted  bigint NOT NULL DEFAULT 0,  -- счётчики пишутся в чекпоинте вместе с offset:
  msgs_not_newer bigint NOT NULL DEFAULT 0,  -- точные (не сбрасываются при рестарте), их
  msgs_invalid   bigint NOT NULL DEFAULT 0,  -- сравнивают e2e и витрина
  updated_at     timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE IF NOT EXISTS stations (
  station_uuid          text PRIMARY KEY,
  occupant_uuid         text,
  occupied_at           bigint,
  last_release_at       bigint,
  last_published_queue  text,           -- канонический JSON строк последней опубликованной очереди; NULL — ещё не публиковалась
  updated_at            timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE IF NOT EXISTS vehicles (
  unit_uuid          text PRIMARY KEY,
  home_station       text    NOT NULL,
  last_ts            bigint  NOT NULL,
  lat                double precision NOT NULL,
  lon                double precision NOT NULL,
  speed_kmh          double precision NOT NULL,
  phase              text    NOT NULL,  -- to_station | waiting | service | served | to_dump
  target_station     text    NOT NULL,
  radius_station     text,              -- станция, в радиусе 50 м которой машина; ведётся в фазе to_station (§3.5)
  radius_entered_at  bigint,            -- вход в радиус radius_station
  arrived_at         bigint,            -- приезд, от которого считается wait_seconds
  dump_visited       boolean NOT NULL,  -- была в радиусе разгрузки на этом плече
  decided            boolean NOT NULL,  -- рекомендация в этом заезде уже считалась
  predicted_start    bigint,            -- service_start, предсказанный при решении (метрика точности)
  updated_at         timestamptz NOT NULL DEFAULT now()
);
```

- Колонки `stations` и `vehicles` один к одному — поля модели ядра (§3.3), с теми же именами. `updated_at` — служебное поле для витрины, в расчёте не участвует.
- `logic_version` — константа в коде, меняется вместе с правилами. `config_hash` — sha256 канонизированного `site.toml`, вместе с `[constants]`. Если они не совпали, а состояние непустое (`next_offset` задан), `dispatcher` отказывается стартовать (`logic_version_changed` или `config_changed`, код 2) и подсказывает `make reset`; если состояния нет, версии просто переписываются. В `stations` и `vehicles` нет `site_id` (одна база — одна площадка), поэтому чужое состояние ищется по всей базе: строка `processor` другой площадки или строки `stations`/`vehicles` при пустом `next_offset` — тоже отказ `config_changed` (§2.4).
- Пишет только `dispatcher`; витрина, `vq-verify` и `tools/e2e.py` только читают.
- Чекпоинт пишет все строки (4 станции и до 40 машин), без отслеживания изменённых.
- `last_published_queue` — `text`, а не `jsonb`: `jsonb` переставляет ключи и нормализует значения, а сравнение (§3.9) идёт по байтам. Хранится ровно та сериализация строк, что уходит в топик (без `at`); `NULL` (не публиковалась) и `'[]'` (опубликована пустая) различаются.
- Числа: времена — `bigint`, координаты и скорость — `double precision` (точный круг для float64), флаги — `boolean`. Загрузка обязана восстановить состояние побитово; это проверяет интеграционный тест (§6.2).

### 2.6 Гарантии и рестарт

- Состояние и offset атомарны: после рестарта нет ни потерянных, ни дважды применённых сообщений.
- Выходы at-least-once. Сообщения после последнего чекпоинта обрабатываются повторно и дают байт в байт те же записи: ядро детерминировано, `at` — время событий.
- Правило для потребителей: текущая очередь станции — запись с наибольшим `vq-src-offset`; запись с `vq-src-offset`, не большим уже виденного, — повтор и игнорируется. Решения дедуплицируются по `(unit_uuid, at)` — эта пара уникальна, так как решение по машине одно на заезд. Правило «наибольший `at`» не годится: за одну секунду очередь станции может публиковаться несколько раз с одним `at`.
- Это прямое отступление от «одинаковые подряд очереди не публикуются»: после падения хвост до одной пачки (≤ 500 входных сообщений) — и очереди, и решения — публикуется повторно, и в логе могут оказаться одинаковые записи подряд. Потребитель схлопывает их по `vq-src-offset` (§3.11 п. 18).
- Зомби — процесс, потерявший партицию, но ещё работающий, — не может записать чекпоинт из-за условия `epoch = мой`. Выходы, которые он успел отправить, совпадают байт в байт с выходами нового владельца, но могут лечь в лог позже его более новых записей того же ключа: остаток пачки и буфер librdkafka уходят после разморозки, до отказа чекпоинта. Поэтому потребитель берёт запись с наибольшим `vq-src-offset`, а не последнюю по позиции. Компакция же оставляет последнюю по позиции: если станция после поздней записи больше не публиковалась, после компакции текущей останется устаревшая очередь. Лечится следующей публикацией станции, полностью — фенсингом продюсера (транзакции Kafka, §2.8 ответ 5); известное ограничение (§10).
- **Время восстановления** = рестарт контейнера + возврат партиции группой + `claim` (одна транзакция на 45 строк, миллисекунды, от длины лога не зависит) + повтор не больше одной пачки. Со static membership перезапущенный процесс получает партицию сразу; standby — только через `session.timeout.ms` (10 с), и после аварии, и после штатной остановки: static-участник не шлёт LeaveGroup (§2.4); без static membership и этих таймаутов после `kill -9` это было бы до 45 с (умолчание librdkafka). Падения подряд удлиняют рестарт: Docker удваивает паузу перед ним (0,1 → 0,2 → … → 60 с, сброс после 10 с работы; пять аварий через 3 с — `claim` через 0,57 … 2,04 с после выхода). Фактическое время измеряет `make e2e-chaos` по часам ВМ Docker: от выхода процесса (`State.FinishedAt`) до старта контейнера, `claim`, нового `epoch` в Postgres и первого чекпоинта; таблица идёт в README. Прототип (Docker Desktop на macOS, все прогоны `make e2e-chaos`, разброс — от нагрузки машины): старт контейнера 0,12–0,33 с, `claim` 0,66–1,14 с, первый чекпоинт 0,70–1,21 с; точка аварии и `kill -KILL -1` дают одинаковые числа; повтор — 1–3 записи, байт в байт. Перехват standby после остановки активного — 10,6–12,3 с.
- **Сбои Postgres** (прототип): заморозка на 25 с — `exit_postgres_stalled` через 15,3 с, `claim` через 5 мс после разморозки; остановка на 20 с — выход сразу, старт ждёт Postgres (§2.4), `claim` через 0,85 с после его старта; обрыв сети на 30 с — выход через 10,4 с (`tcp_user_timeout`), `claim` через 0,2 с после восстановления сети. После всех трёх `vq-verify` — без расхождений, повторы байт в байт.
- Решения, выданные в окне восстановления, опаздывают, но не теряются; генератор исполняет их, пока машина не начала обслуживание (§4.3), а если не успел — модель сходится сама (§3.5: самолечение у фактической станции или конец заезда в радиусе разгрузки).
- Полный перепрогон (`make reset` и та же телеметрия) воспроизводит те же записи; он корректен только для тех же `logic_version` и `config_hash` — это и есть `make verify`.
- Стенд — одна нода Redpanda с RF=1 в режиме dev-container (без fsync): потеря ноды — потеря данных с любым брокером. В продакшене RF=3, `acks=all`, `min.insync.replicas=2`. Оговорка — в README.

### 2.7 Детерминизм

Выходы — чистая функция последовательности сообщений `telemetry.v1` в порядке лога:

- одна партиция — один полный порядок;
- «сейчас» берётся из `ts` в payload; timestamp записи Kafka не используется;
- ETA отсчитывается от `ts` позиции машины, а не от «сейчас»;
- арифметика в целых секундах, одно округление на длительность (§3.2);
- нет часов компьютера, таймеров, случайности, итерации по неупорядоченным множествам;
- сообщения применяются по одному, поэтому границы пачек не влияют на результат.

Следствие: запись `telemetry.v1`, прогнанная через ядро офлайн с любой скоростью, даёт те же `queue.v1` и `decision.v1`. Это проверяет `make verify` (§6.3).

Детерминизм гарантирован для тройки «код + `site.toml` + образ» (версия Python и libm влияют на последний бит гаверсинуса). Поэтому `make verify` и `make bench` запускаются в образе приложения (`docker compose run --rm dispatcher vq-verify`; `vq-bench` — с `--no-deps`: брокер и БД ему не нужны). В прототипе хэш выходов `make bench` на хосте macOS и в образе Linux совпал, но вне образа это не гарантия: отсчёты плеч после рекомендации не защищены зазором от порога 50 м (§4.2, §10).

### 2.8 Ответы для `ARCHITECTURE.md` (черновик)

1. **Сколько процессоров и критерий.** Один — `dispatcher`; генератор и витрина процессорами не являются: первый — источник данных, вторая только читает результаты. Критерий: *отдельный процессор выделяется там, где меняется домен согласованности — состояние, которое нужно читать и менять атомарно в едином порядке событий.* Очереди, решения и «сейчас» — один домен (площадка), поэтому процессор один.
2. **Ключ и состояние.** Логический ключ — площадка; физически это единственная партиция `telemetry.v1`. Состояние в Postgres: машины (последний `ts`, позиция и скорость, фаза, своя и целевая станции, станция, в радиусе которой машина, и момент входа в него, приезд, флаг «была в радиусе разгрузки», флаг решения, предсказанное начало обслуживания), станции (занявшая машина, момент занятия, последнее освобождение, последняя опубликованная очередь), «сейчас», offset, `epoch`, точные счётчики сообщений, `logic_version` и `config_hash`.
3. **Машины, станции и решение.** Перекладываем всё на ключ площадки: одна партиция даёт всю площадку в едином порядке, и телеметрия по машинам, очереди по станциям и решение считаются в одном процессе над общим состоянием. Решение читает очереди всех станций и в том же шаге переносит машину между двумя очередями, поэтому следующая машина видит результат и две машины не отправляются на одну свободную станцию. Ключ входных сообщений остаётся `unit_uuid` по контракту; партиционирование — по площадке.
4. **Партиции и параллелизм.** `telemetry.v1` — одна партиция на площадку. Ключ `unit_uuid` задан контрактом, и стандартный партиционер разнёс бы машины одной площадки по разным партициям; поэтому при N площадках либо продюсеры телеметрии используют партиционер по площадке (машина → площадка из справочника), либо — если вход внешний и его не изменить — перед процессором ставится маленький этап-секвенсор: он читает многопартиционный вход и перекладывает каждую машину в партицию её площадки, а детерминизм отсчитывается уже от этого топика. `queue.v1` и `decision.v1` — по одной партиции: порядок по ключу сохранился бы при любом их числе, но потребителей мало, и одной хватает. Реплики топиков: на стенде RF=1 (одна нода Redpanda), в продакшене RF=3 с `acks=all` и `min.insync.replicas=2` (§2.6). Реплик `dispatcher` может быть несколько, активна одна на партицию: у standby свой `group.instance.id`, который сортируется после id активного (range-ассайнер отдаёт единственную партицию первому static-участнику, §2.4); вход standby — ребаланс, активный заново делает `claim` (пауза до ~0,4 с), поэтому standby в compose по умолчанию не запущен. Параллелизм ограничен числом площадок: глобальное «сейчас» и решение по всем станциям требуют единого порядка. Внутри площадки рост упирается в пересчёт всех очередей на каждое сообщение: O(машин) на сообщение, O(машин²) в секунду. Цифры: 40 сообщений/с ≈ 4 КБ/с входа (в среднем 102 Б на сообщение); ~4 чекпоинта в секунду, пока процессор не отстаёт (пачка — до 500 сообщений или 0,25 с); ядро — 72–76 мкс на сообщение в образе (`make bench`: час замкнутого контура, 144 723 сообщения, §6.4), ~0,3 % одного ядра CPU; 400 машин на тех же 4 станциях — ~600 мкс на сообщение, ~24 % ядра (разовый замер на хосте; `make bench` число машин не меняет); предел одного ядра — порядка 700–800 машин на площадку, дальше нужен инкрементальный пересчёт.
5. **Гарантии доставки.** Транзакционность нужна там, где два изменения обязаны быть атомарными: состояние и offset — одна транзакция Postgres, иначе рестарт либо теряет, либо дважды применяет сообщения. Для выходов достаточно идемпотентности, гарантия — at-least-once. Потерь нет: выходы пачки уходят с `acks=all`, и чекпоинт пишется только после `flush` (§2.4); продюсер идемпотентный (`enable.idempotence=true`), поэтому ретраи librdkafka не дают дублей и не переставляют записи. Повтор после падения — та же запись с тем же `vq-src-offset`: выход — детерминированная функция входа; текущая очередь станции — запись с наибольшим `vq-src-offset`; `decision.v1` дедуплицируется по `(unit_uuid, at)`. Цена — возможные после падения одинаковые записи подряд (отступление от ТЗ, §3.11 п. 18). Альтернатива — Kafka-транзакции со снимком состояния в compacted-топике в той же транзакции: выходы exactly-once и одна система, но больше подводных камней (LSO, compaction транзакционных топиков, таймауты транзакций) и нет SQL-доступа к состоянию. Переходить на неё стоит, когда появится потребитель решений без дедупликации или понадобится, чтобы компакция `queue.v1` не оставляла позднюю запись зомби (§2.6).
6. **Рестарт.** Состояние читается из Postgres одной транзакцией — миллисекунды, от длины лога не зависит. Полное время — по §2.6: рестарт контейнера, возврат партиции (сразу со static membership; standby — через `session.timeout.ms`, и после штатной остановки тоже: static-участник не шлёт LeaveGroup), повтор не больше одной пачки. Измерено `make e2e-chaos` (точка аварии после отправки пачки и `kill -KILL -1` внутри контейнера, часы ВМ Docker): от выхода процесса до `claim` 0,66–1,14 с, до первого чекпоинта 0,70–1,21 с; повтор — записи одной пачки (1–3 записи `queue.v1`, байт в байт); перехват standby — 10,6–12,3 с. Сообщения после последнего чекпоинта обрабатываются повторно и дают те же записи; потребители отбрасывают повторы по правилу из ответа 5, генератор — по `(unit_uuid, at)` и по заезду. Полный перепрогон топика той же версией логики воспроизводит все записи байт в байт. Перепрогона другой версией логики на месте нет: при сохранённом состоянии `dispatcher` с другой `logic_version` или `config_hash` не стартует (§2.5), а `make reset` удаляет лог вместе с выданными решениями.
7. **Что не выносили.** (а) Дедупликацию и определение фазы по машинам с ключом `unit_uuid` — им нужен глобальный «сейчас», а лишний топик добавляет задержку и вторую границу согласованности. (б) Очереди по станциям — решение меняет состав очередей; разделение даёт цикл через Kafka и гонки решений. (в) Само решение — ему нужно атомарно читать все очереди и менять две. Вынесена только витрина: она лишь читает.

## 3. Ядро расчёта

`src/vq/core` — чистый код: без I/O, часов, случайности и сторонних зависимостей.

### 3.1 Конфигурация

`config/site.toml` — общий для сервиса и генератора. Файл генерирует `tools/make_site.py` (`--check` сверяет его с генерацией), руками он не правится:

- `site.id`;
- `dump` — координаты точки разгрузки;
- `stations` — четыре станции: `uuid`, `lat`, `lon`;
- `assignment` — закрепление 40 машин за станциями;
- `constants` — константы ТЗ: обслуживание 200 с (`service_s`), манёвр 30 с (`maneuver_s`; занятие 230 с), расчётная скорость 10 м/с (`speed_mps`), радиус 50 м (`radius_m`), порог «стоит» 1 км/ч (`stop_kmh`), радиус решения 1500 м (`decision_radius_m`), горизонт 1800 с (`horizon_s`), свежесть 30 с (`fresh_s`), минимальный выигрыш 60 с (`min_gain_s`). Умолчания в коде — те же значения. Секция записана в файл и поэтому входит в `config_hash` (§2.5): смена констант, как и любого значения `site.toml`, при непустом состоянии требует `make reset`.

Проверки при загрузке; любая ошибка — `ConfigError`, процесс не стартует:

- геометрия: радиусы 50 м станций не пересекаются (станции не ближе 100 м друг к другу); разгрузка дальше 1550 м (радиус решения + радиус) от каждой станции, поэтому её радиус лежит вне зоны решения и не пересекается ни с одним радиусом станции;
- закрепление: каждая машина — ровно за одной станцией, и эта станция есть в списке; `uuid` станций не повторяются;
- структура и типы: есть `[site]`, `[dump]`, `[[stations]]`, `[assignment]`; `site.id` и `uuid` — строки; закрепление — списки строк; координаты — конечные числа TOML (не строки и не `bool`), `|lat| ≤ 90`, `|lon| ≤ 180`; константы — конечные числа, неизвестный ключ — ошибка; `service_s`, `maneuver_s`, `horizon_s`, `fresh_s`, `min_gain_s` — целые (§3.2); все константы больше нуля, кроме `min_gain_s ≥ 0`.

Без этих проверок `lat = nan` (валидный TOML) молча дал бы станцию, которую нельзя занять, а `service_s = 200.0` — дробные `wait_seconds` на выходе.

### 3.2 Время, расстояние, формат

- Время — целые секунды epoch. `ts` должен быть целым числом (допускается float с целым значением), иначе сообщение невалидно.
- Расстояние — формула гаверсинусов, R = 6 371 008,8 м («по прямой между координатами»).
- Время пути на `d` метров: `rhu(d / 10)`, где `rhu(x) = floor(x + 0.5)` — округление половины вверх. Встроенный `round()` банковский и не используется. Для машины «к разгрузке» оба плеча складываются и сумма округляется один раз.
- Пороги строгие: «в радиусе» — `d < 50`, «стоит» — `speed_kmh < 1`, зона решения — `d < 1500`. Ровно 50 м — снаружи.
- Время на выходе — `YYYY-MM-DDTHH:MM:SSZ`, UTC.

### 3.3 Модель

**Машина** (`Vehicle`; поля — колонки `vehicles` в том же порядке, §2.5): `unit_uuid`, `home_station` (ниже — `home`), `last_ts`, `lat`, `lon`, `speed_kmh`, `phase`, `target_station` (ниже — `target`), `radius_station`, `radius_entered_at`, `arrived_at`, `dump_visited`, `decided`, `predicted_start`. `radius_station` — станция, в радиусе 50 м которой машина, `radius_entered_at` — момент входа в этот радиус. В фазе `to_station` они ведутся по любой станции, не только по целевой (§3.5); в фазах `waiting`, `service` и `served` это станция, у которой машина встала (она же целевая), и вход в её радиус; в `to_dump` — пусто.

| Фаза | Смысл | Состояние по ТЗ |
|---|---|---|
| `to_station` | едет к целевой станции | к станции |
| `waiting` | стоит в радиусе целевой станции, занятой другой машиной | на станции |
| `service` | занимает целевую станцию | на станции |
| `served` | освобождена таймером, но ещё в радиусе | — (наша) |
| `to_dump` | вышла из радиуса станции после обслуживания | к разгрузке |

Целевая станция (`target`) — своя (`home`); после рекомендации — рекомендованная, после самолечения — та, у которой машина встала (§3.5); с концом заезда — снова своя.

**Станция** (`Station`; поля — колонки `stations`): `station_uuid`, `occupant_uuid` (ниже — `occupant`), `occupied_at`, `last_release_at`, `last_published_queue` (ниже — `last_published`: строки последней опубликованной очереди).

**Площадка** (`SiteState`): `now` (`None` до первого учтённого сообщения), машины, станции.

Машина свежая, если `now − last_ts ≤ 30`.

### 3.4 Обработка одного сообщения

`Engine.apply(raw: bytes | None) -> StepResult(outputs, events)`. Шаги строго по порядку:

1. **Разбор.** Значение записи — JSON-объект в строгом UTF-8 (контракт топика; пустое значение, UTF-16/32, BOM и битые байты — невалидно) с полями `unit_uuid` (строка), `ts` (целое), `lat`, `lon`, `speed_kmh` (числа; `bool` числом не считается); `unit_uuid` есть в закреплении. `json.loads` с запретом `NaN`/`Infinity`; все числа конечные; `|lat| ≤ 90`, `|lon| ≤ 180`, `0 ≤ speed_kmh < 300`; `ts` в диапазоне 2001–2100 (`1 000 000 000 ≤ ts < 4 102 444 800`) — это ловит миллисекунды и не зависит от «сейчас»; float-`ts` с целым значением приводится к `int`. Иначе — событие `invalid`, состояние не меняется.
2. **Дубли и порядок.** Если у машины уже есть учтённое сообщение и `ts ≤ last_ts` — событие `not_newer`, состояние не меняется. Опоздавшее, но более новое сообщение учитывается.
3. **«Сейчас».** `now = max(now, ts)`.
4. **Таймеры.** Пока есть станция с `occupied_at + 230 ≤ now`: выбрать станцию с наименьшим `R = occupied_at + 230` (при равенстве — по `station_uuid`), освободить по таймеру и передать (§3.6).
5. **Переход машины** по сообщению (§3.5). Может занять или освободить станцию.
6. **Рекомендация**, если сработал триггер (§3.8).
7. **Очереди** всех станций пересчитываются на `now`, изменившиеся публикуются (§3.9).

Невалидные и не новые сообщения не дают выходов и не двигают «сейчас».

### 3.5 Переходы машины

Обозначения для текущего сообщения: `T` — целевая станция машины; `Z` — станция, в радиусе 50 м которой машина, или пусто (радиусы не пересекаются, §3.1, поэтому такая станция одна); `inT` — расстояние до `T` меньше 50 м; `stopped` — `speed_kmh < 1`; `inDump` — расстояние до разгрузки меньше 50 м. Позиция, скорость и `last_ts` обновляются всегда.

Первое учтённое сообщение машины создаёт её с `target = home`, `decided = false`, `phase = to_station`, а затем применяются строки для `to_station`. Поэтому машина, которая с первого сообщения стоит в радиусе станции, сразу занимает её или встаёт ждать (у чужой станции — через самолечение), а машина, чьё первое сообщение в радиусе разгрузки, сразу заканчивает пустой заезд без события и становится «к станции», выйдя из радиуса разгрузки.

В фазе `to_station` первая строка применяется всегда, затем — подходящая из двух следующих.

| Фаза | Условие | Действие |
|---|---|---|
| `to_station` | всегда, первой | **вход в радиус:** если `Z ≠ radius_station` — `radius_station = Z`, `radius_entered_at = ts` (оба пусто, если `Z` пусто). Так `radius_entered_at` — вход в радиус той станции, у которой машина сейчас, целевой или нет: выход из радиуса его стирает, прыжок из радиуса в радиус между сообщениями даёт новый вход |
| `to_station` | `inDump` | «конец заезда», затем `dump_visited = true`; если заезд был (`decided` или `T ≠ home`) — событие `fsm_resync{station = T}` с прежней целью |
| `to_station` | не `inDump`, `stopped`, `Z` не пусто | если `Z ≠ T` — **самолечение:** `target = Z`, событие `fsm_resync{station = Z}`, `decided` не меняется (нового решения нет). Затем станция `Z` свободна → **занятие** по сообщению (§3.6), `arrived_at = ts`; занята → `phase = waiting`, `arrived_at = radius_entered_at` (вход в радиус `Z`, а не остановка) |
| `waiting` | `inT`, `stopped`, станция `T` свободна | **занятие** по сообщению (§3.6), `arrived_at` не меняется |
| `waiting` | не `inT` | уехала необслуженной: `phase = to_station`, `radius_station = radius_entered_at = arrived_at = пусто` |
| `service` | не `inT` | **освобождение** `T` по выходу в момент `max(ts, occupied_at)` и передача (§3.6); затем «конец заезда» |
| `served` | не `inT` | «конец заезда» (станция уже освобождена таймером) |
| `to_dump` | `inDump` | `dump_visited = true` |
| `to_dump` | не `inDump`, `dump_visited` | `phase = to_station`, `dump_visited = false`, `radius_station = radius_entered_at = пусто` |

«Конец заезда»: `phase = to_dump`, `target = home`, `decided = false`, `dump_visited = false`, `radius_station = radius_entered_at = arrived_at = predicted_start = пусто`. Прогноз принадлежит заезду: заезд, кончившийся без занятия (правило разгрузки), уносит его с собой.

Остальные сочетания ничего не меняют. Проезд через радиус любой станции на скорости выходов не меняет: запоминается только вход.

Остановка у нецелевой станции в фазе «к станции» значит приезд к ней (самолечение, решение 14.10): так модель сходится с миром, если рекомендация не была исполнена — опоздала, потерялась или генератор перезапустился. Приезд к ней считается так же, как к целевой: у занятой станции — вход в радиус, а не остановка (ТЗ: «её приезд считается наступившим в момент входа в радиус»). Иначе машина, въехавшая раньше, но вставшая позже, проигрывала бы в FIFO въехавшей позже, и цепочка занятий модели расходилась бы с миром.

«К станции» в радиусе разгрузки — конец заезда (решение 14.10). По таблице состояний ТЗ «к станции» начинается с выхода из радиуса разгрузки, а в радиусах разгрузки и станции сразу быть нельзя (≥ 1550 м, §3.1). Значит, машину, которую модель держала «к станции» (например, считала ждущей, а её обслужили), мир уже обслужил; без этого правила она весь цикл стояла бы фантомной строкой в чужой очереди, а на следующем подъезде к своей станции осталась бы без решения. Первое сообщение машины в радиусе разгрузки заканчивает пустой заезд без события: строка «к разгрузке» после разгрузки считается так же, как «к станции» (§3.7), и выходы те же.

С послушным генератором самолечения и концов заезда с событием нет, и выходы не меняются; срабатывания обоих правил видны в метрике `vq_fsm_resync_total`. Оба правила действуют только в фазе `to_station`: ждущая, уехавшая необслуженной, получает строки `to_station` со следующего сообщения.

### 3.6 Занятие, освобождение, передача

- **Занятие** станции `S` машиной `v` по сообщению с `ts`: момент занятия `t = max(ts, S.last_release_at)`; при передаче — `t = max(R, v.arrived_at)`. Так опоздавшие сообщения не дают перекрывающихся занятий и отрицательного ожидания (§3.11 п. 19). Дальше `S.occupant = v`, `S.occupied_at = t`, `v.phase = service`. Если у `v` задан `predicted_start` — событие `prediction_error = t − predicted_start`, затем `predicted_start = пусто`.
- **Освобождение** в момент `R`: по таймеру `R = occupied_at + 230`, по выходу `R = max(ts, occupied_at)`, где `ts` — время первого сообщения занявшей машины вне радиуса (выход всегда раньше таймера, иначе таймер уже сработал на шаге 4). `max` — для опоздавших сообщений: опоздавшее стояние могло сдвинуть `occupied_at` вперёд, к последнему освобождению, и `R = ts` дал бы занятие отрицательной длины и `last_release_at`, идущий назад (§3.11 п. 19). `S.occupant = пусто`, `S.last_release_at = R`; при таймере занявшая получает `phase = served`.
- **Передача** сразу после освобождения. Кандидаты — машины с `phase = waiting` и `target = S`, свежие на `now` и стоящие (`speed_kmh < 1`) в последнем учтённом сообщении. Станция переходит к минимальной по `(arrived_at, unit_uuid)`, момент занятия — `max(R, arrived_at)` (первый пункт). Если кандидатов нет, станция свободна, и её займёт первое учтённое сообщение машины, стоящей в радиусе (правило 1 буквально).
- Применённые переходы не пересматриваются: запоздавший выход занявшей машины после срабатывания таймера меняет только её собственную фазу.
- Таймеры проверяются только на шаге 4. Если сообщение, опоздавшее на 230 с и больше, занимает станцию так, что `occupied_at + 230 ≤ now`, занятие держится до следующего учтённого сообщения, и на его шаге 4 станция освобождается таймером с тем же `R = occupied_at + 230`. Это известное ограничение (§10); ТЗ ограничивает опоздание 60 с.

### 3.7 Очередь станции

Строки очереди станции `S` на момент `now`:

1. **Занявшая** `o` — всегда, даже если она несвежая: `eta = null`, `service_start = occupied_at`, `free_at = occupied_at + 230`, `wait_seconds = occupied_at − o.arrived_at`.
2. **Кандидаты** — только свежие машины, кроме занявшей:
   - `waiting` с `target = S`: приезд `a = arrived_at`, `eta = null`, вид 0;
   - `to_station` с `target = S`: `eta = last_ts + rhu(dist(позиция, S) / 10)`, `a = eta`, вид 1;
   - `to_dump` с `home = S`: пока `dump_visited = false` — `eta = last_ts + rhu((dist(позиция, разгрузка) + dist(разгрузка, S)) / 10)`; после захода в радиус разгрузки (разгрузка мгновенная) — `eta = last_ts + rhu(dist(позиция, S) / 10)`; `a = eta`, вид 1.

   Кандидат с `eta > now + 1800` в очередь не попадает.
3. **Порядок** кандидатов — по `(a, вид, unit_uuid)`.
4. **Цепочка.** Начало `prev` — `free_at` занявшей, а если её нет — `S.last_release_at` (или −∞). Для каждого кандидата: `service_start = max(a, prev)`, `free_at = service_start + 230`, `wait_seconds = service_start − a`, `prev = free_at`.

Строка очереди: `{"unit_uuid", "eta", "service_start", "free_at", "wait_seconds"}`. Машины в фазе `served` ни в какую очередь не попадают; каждая машина — не более чем в одной очереди и одной строкой.

### 3.8 Рекомендация

**Триггер:** после шага 5 машина в фазе `to_station`, `decided = false` и `dist(позиция, home) < 1500`. Тогда `decided = true` и:

1. Если `now − ts > 30` — отказ `stale_telemetry`.
2. Иначе для каждой станции `X`:
   - `eta_X = ts + rhu(dist(позиция, X) / 10)`;
   - строки очереди `X` по §3.7, но без этой машины;
   - ключ машины — `(eta_X, 1, unit_uuid)`; предшественник — последняя строка с меньшим ключом (занявшая всегда раньше);
   - `prev` — `free_at` предшественника, а если его нет — начало цепочки из §3.7 п. 4 (у свободной станции — последнее освобождение, §3.11 п. 9);
   - `wait_X = max(0, prev − eta_X)`.
3. Выбор `X*` — минимум по `(wait_X, X ≠ home, dist(позиция, X), X)`.
4. `gain = wait_home − wait_X*`. Если `X* = home` или `gain < 60` — отказ `no_gain`. Иначе — `recommended`: `target = X*`; `radius_station` и `radius_entered_at` не меняются: вход в радиус — геометрия, а не намерение (§3.5).
5. Для метрики точности: `predicted_start = eta_X* + wait_X*` при `recommended`, `eta_home + wait_home` при `no_gain`; при `stale_telemetry` прогноза нет. Прогноз снимают занятие (§3.6) и конец заезда (§3.5), поэтому `prediction_error` сравнивает занятие только с решением того же заезда. Критерий точности — §6.1.
6. Выход `decision.v1` с `at = now`.

Решения принимаются строго в порядке лога и сразу меняют состояние, поэтому решение следующей машины видит перенаправленные раньше.

### 3.9 Публикация и форматы

После шага 6 очередь каждой станции строится заново (станции — в порядке `station_uuid`). Если её строки отличаются от `last_published`, выдаётся запись `queue.v1` с `at = now`, и `last_published` обновляется. Сравниваются только строки; `at` в сравнении не участвует. Пустая очередь `[]` тоже публикуется. При первом расчёте (`last_published` пусто) очередь публикуется как исходная.

Внутри шага сначала идёт решение, затем очереди. Каждая запись несёт заголовок `vq-src-offset` (§2.3). Сериализация — `json.dumps(obj, separators=(",", ":"), ensure_ascii=False)`, ключи в порядке ТЗ, значение в UTF-8. Ключ записи — `station_uuid` для очереди и `unit_uuid` для решения.

```json
{"station_uuid":"S1","at":"2026-09-15T12:00:00Z","queue":[{"unit_uuid":"T1","eta":null,"service_start":"2026-09-15T11:59:00Z","free_at":"2026-09-15T12:02:50Z","wait_seconds":0}]}
{"unit_uuid":"T4","at":"2026-09-15T12:00:00Z","result":"recommended","from_station":"S1","to_station":"S2","gain_seconds":80}
{"unit_uuid":"T4","at":"2026-09-15T12:00:00Z","result":"rejected","reason":"no_gain"}
```

### 3.10 События ядра

`accepted`, `invalid`, `not_newer`, `fsm_resync{station}` (самолечение — станция остановки; конец заезда в радиусе разгрузки — прежняя цель), `occupied{station, how=arrival|handover, unit}`, `released{station, reason=timer|exit}`, `decision{result, reason, gain}` (`gain` — кроме `stale_telemetry`; у `recommended` `reason` пустой), `prediction_error{seconds}`, `queue_published{station, length}`. Ядро только возвращает события; счётчики ведёт `dispatcher` после успешного чекпоинта.

## 4. Генератор

### 4.1 Площадка

- Площадка `site-1`. Разгрузка — `49.1288, 142.6601` (координаты из образца в ТЗ).
- Станции S1–S4 — ровно 10 000 м от разгрузки по азимутам 0°, 10°, 20°, 30°. Соседние станции — около 1 743 м друг от друга, S1–S4 — около 5 176 м.
- Закрепление: S1 — 13 машин (`T-01`…`T-13`), S2 — 11, S3 — 9, S4 — 7. Нагрузка ρ = n·230 / (230 + 2000) ≈ 1,34 / 1,13 / 0,93 / 0,72: S1 перегружена, S4 недогружена, поэтому будут и живые очереди, и смесь `recommended` и `no_gain`.
- `tools/make_site.py` (§3.1) считает координаты точкой по азимуту и дальности на сфере, с полной точностью float, и пишет закрепление и `[constants]` со значениями ТЗ.
- Тест конфигурации (`test_config.py`, §6.1): проверки из §3.1, расстояния этого пункта, совпадение файла с генерацией, маршруты разгрузка ↔ станция не ближе 100 м к чужим станциям, зазор отсчётов от порогов (§4.2).

### 4.2 Симуляция

`src/vq/generator/sim.py` — чистый код: без Kafka, часов и I/O, случайность — только экземпляры `random.Random(seed)`. Так же устроены инжектор сбоев (`faults.py`, §4.5) и замкнутый контур в памяти (`closed_loop.py`: симулятор → сбои → ядро → решения обратно в симулятор; его используют тест замкнутого контура и `vq-bench`); чистоту всех трёх проверяет AST-тест в `test_determinism.py` (§6.1). Тик — 1 секунда симуляции; на каждом тике каждая машина даёт одно сообщение.

Состояния машины: `drive` (отрезок к точке станции или разгрузки), `arrived`, `queued`, `serving`, `maneuver`. Станция хранит занявшую машину со временем начала и FIFO ждущих по `(radius_entered_at, unit_uuid)` — тот же ключ, что у ядра (§3.6): в ядре приезд к занятой станции — тоже вход в радиус, в том числе у машины, которую ядро перевело к станции самолечением (§3.5).

Тик `t`:

1. Применить полученные рекомендации (§4.3).
2. Станции: если у занявшей `start + 230 ≤ t`, станция свободна; свободная станция с непустой FIFO передаётся голове очереди со `start = t`.
3. Машины, по `unit_uuid`:
   - `drive`: шаг `min(10 м, остаток)` по дуге большого круга, `speed_kmh = max(шаг × 3,6, 1,0)` (на коротком последнем шаге машина не должна выглядеть стоящей раньше, чем генератор считает её прибывшей). При первом входе в радиус 50 м целевой станции запоминается `radius_entered_at`. Достигнув точки станции — `arrived`. Достигнув разгрузки — мгновенная разгрузка, и остаток 10-метрового шага этого тика идёт уже по новому отрезку к своей станции (`speed_kmh = 36`): иначе отсчёты обратного плеча ложились бы ровно на пороги 50 и 1500 м.
   - `arrived` (тик после прибытия, скорость 0): станция свободна и FIFO пуста — `serving` со `start = t`; иначе — `queued`.
   - `queued`: стоит в точке станции, скорость 0.
   - `serving`: стоит до `start + 199`. С `start + 200` — `maneuver`: отъезд в сторону разгрузки на `(радиус + 1 м) / манёвр` = 51 / 30 = 1,7 м/с (6,12 км/ч), на тике `start + 200 + k` машина в `1,7·k` м от точки станции. На `start + 229` она в 49,3 м, на `start + 230` — в 51 м, вне радиуса; дальше `drive` к разгрузке на 10 м/с. Скорость манёвра выводится из констант `[constants]`, а не задана числом.
4. Зона решения (только для метрики задержки): машина в `drive` к своей станции, не перенаправленная в этом заезде, впервые ближе 1500 м — `zone_entered_at = t`.
5. Сообщения тика уходят в инжектор сбоев (§4.5), затем в `telemetry.v1` с ключом `unit_uuid`.

Пороги генератора (зона 1500 м, радиус 50 м станции) считаются `vq.geo.haversine` от тех же float, что уходят в сообщение, и в том же порядке аргументов, что у ядра; `lat`/`lon` пишутся с полной точностью (`repr(float)`), без округления до 4 знаков, как в образце ТЗ. Поэтому в одном образе симулятор и ядро сравнивают с порогом одно и то же число и согласны побитово (замкнутый контур, e2e, `verify`).

Зазор от порогов нужен только перепрогону на другой платформе, где последний бит гаверсинуса может отличаться (§2.7). Отсчёты плеч разгрузка ↔ своя станция на пороги ядра не попадают: длины плеч кратны 10 м, старт сдвинут на 3 м (§4.4), остаток шага при разгрузке переносится на обратное плечо. На 3 часах без решений и сбоев (seed 42) отсчёты лежат не ближе 0,7 м к порогу 50 м станции (манёвр: 49,3 м на +229), не ближе 1 м к порогам 1500 м и 50 м разгрузки (3 м — в первом заезде), дробная часть `d/10` — не ближе 0,2 к точке округления `rhu`; `test_config` требует ≥ 0,5 м и ≥ 0,005. Плечи после рекомендации зазором не защищены: расстояние до рекомендованной станции произвольно (из 3612 возможных плеч у 448 отсчёт ближе 0,5 м к её радиусу, худший — 0,0005 м).

Так прогноз сервиса совпадает с «реальностью»: освобождение по таймеру и выезд из радиуса приходятся на одну секунду, а передача у генератора и у сервиса идёт по одному ключу.

### 4.3 Рекомендации

- Отдельный поток читает `decision.v1`: `assign` партиции 0 без группы и коммитов, с offset, равным high watermark на момент старта, — до первого тика, поэтому решения прошлых прогонов не исполняются. Записи отдаются основному циклу по одной, без накопления пачки (при ×N каждая секунда удержания стоила бы N секунд симуляции), и применяются в начале следующего тика.
- Повторы отсеиваются по `(unit_uuid, at)` (счётчик `decisions.duplicates` в итоге). Запись не по контракту — не JSON, неизвестная машина или станция, рекомендация на свою станцию — считается в `ignored{invalid}`; генератор ни на какой записи не падает.
- `recommended` применяется, если в этом заезде машина ещё не начала обслуживание (`drive` к своей станции, `arrived` или `queued` у неё), ещё не перенаправлена и `at ≥ trip_started_at` (тик разгрузки; для первого заезда — тик старта). Машина в `queued` удаляется из FIFO своей станции. Новый отрезок — от текущей позиции к точке рекомендованной станции, `redirected = true`. Иначе — счётчик проигнорированных с причиной `already_serving` (`serving`, `maneuver` или `drive` к разгрузке) или `stale_trip` (решение прошлого заезда или вторая рекомендация в этом). Если машина всё же не успела, модель сходится сама: самолечением при остановке у фактической станции или концом заезда в радиусе разгрузки (§3.5).
- После обслуживания и разгрузки машина снова едет к своей станции: `redirected = false`, `zone_entered_at = пусто`, `trip_started_at = t`.
- Синхронного ожидания нет. При ускорении ×N поворот запаздывает на «задержка обработки × N» секунд симуляции; это видно в метрике `vq_gen_decision_delay_sim_seconds` (§4.6). Замкнутый контур рассчитан на ускорение до ×20, на нём идёт e2e (`ignored{already_serving}` = 0). `--speed max` — только вместе с `--no-decisions` (иначе отказ с кодом 2): без пауз рекомендации не успевают вернуться. Такой прогон — запись телеметрии без обратной связи (нагрузка, `verify`), а не сценарий замкнутого контура.

### 4.4 Темп, старт, остановка

- `--speed 1|N|max`: тик `k` уходит в момент `start_wall + k / N` по монотонным часам, без накопления ошибки; `max` — без пауз. Демо-генератор `make up` идёт с `--speed ${VQ_SPEED:-1}` (§2.2).
- Генератор стартует только на пустом `telemetry.v1` — в который ещё ничего не писали (high watermark = 0: записи, удалённые retention, всё равно оставили фазы в `dispatcher`); иначе отказывается (код 1) с подсказкой `make reset`: новая смена с новыми позициями противоречила бы фазам, сохранённым в `dispatcher`. Часы стартуют с текущего времени.
- Флаг `--allow-dirty` — для демо: с ним запускается демо-генератор `make up` (§2.2), потому что `make down` сохраняет тома и повторный `make up` идёт по непустому топику. Генератор пишет WARNING `dirty_start`, часы стартуют с `max(текущее время, максимальный ts за последние 1000 записей + 1)` — не по последней записи, потому что в хвосте лежат дубли и опоздания со старыми `ts`; невалидные записи хвоста пропускаются. `dispatcher` продолжает с последнего чекпоинта, модель сходится примерно за цикл (§10). Точные счётчики `processor` накопительные, а ожидаемые отбросы генератора — за запуск, поэтому после такого рестарта «отброшено = ожидалось» не сходится; это равенство проверяет `make e2e` после `make reset`.
- Старт машин: на отрезке от разгрузки к своей станции, на расстоянии `1603 + 10·k` м от станции, `k` — случайное из `{0…839}` по seed; все едут к станции и передают с первого тика, первое сообщение — после первого 10-метрового шага. При `k ≥ 836` (4 положения из 840) оно лежит в радиусе разгрузки, и ядро начинает такой заезд по правилу разгрузки (§3.5) — без события и с теми же выходами, что у «к станции».
- Продюсер: `enable.idempotence=true`, `acks=all` — иначе ретраи переставили бы сообщения и сломали равенство «отброшено = ожидаемые отбросы». Если локальная очередь librdkafka переполнена (`BufferError`, так бывает при `--speed max`), `produce()` повторяется после `poll()`.
- `--duration` (секунды симуляции) — для e2e и записи телеметрии без обратной связи (§4.3). По окончании генератор досылает отложенные дубли, опоздания и обрывы в их порядке (§4.5), ждёт доставки (`flush`), пишет итог строкой лога `summary` (поле `summary`) и в `/out/summary.json` (`--summary`) и завершается. Так же — по SIGTERM/SIGINT. После исключения в цикле итог тоже пишется, но отложенное не досылается: доставляется только уже отправленное.
- Итог: `produced`, `faults{dup, late, outage}`, `expected_drops`, `decisions{received, applied, ignored{already_serving, stale_trip, invalid}, duplicates}`, `ticks`, `start_ts`, `last_ts`, `seed`, `speed`, `stopped_by` (`duration | SIGTERM | SIGINT | kafka_fatal | error`), `delivery_failed`, `error` (`null` — норма). `invalid` есть, только если такие записи были.
- Коды выхода: 0 — норма, в том числе SIGTERM/SIGINT; 1 — отказ старта (непустой топик без `--allow-dirty`, Kafka или `decision.v1` недоступны, ошибка конфигурации) или сбой прогона (ошибка доставки, остаток после `flush`, фатальная ошибка продюсера, исключение в цикле; итог при этом пишется); 2 — неверные аргументы.
- Лог — JSON-строки в stdout, формат общий с `dispatcher` (`vq.logs`, §2.4); итог прогона — строка `summary`.

### 4.5 Сбои

Параметры: `--seed` (по умолчанию 42), `--dup-rate` (по умолчанию 0,005), `--late-rate` (0,002), `--outage-rate` (0,0005 на машину за тик). Инжектор детерминирован по seed (свой экземпляр `random.Random`).

- **Дубль:** копия сообщения отправляется ещё раз через 0–60 с, в любом месте.
- **Опоздание:** сообщение задерживается на 2–60 с. Только на дороге — дальше 100 м от станций и разгрузки.
- **Обрыв связи:** машина копит сообщения 5–60 с, потом отправляет накопленное по порядку `ts`. Начинается, только если машина дальше 700 м от станций и разгрузки, чтобы обрыв закончился до подъезда.
- Порядок отправки на тике: текущие сообщения по `unit_uuid`, затем назначенные на этот тик дубли и опоздания (в порядке назначения), затем досылка обрывов. Сообщение тика, на котором обрыв кончается, входит в досылку последним. В конце прогона — назначенные дубли и опоздания по времени, затем буферы обрывов по `unit_uuid`.
- Ожидаемые отбросы: генератор применяет правило «`ts` не больше последнего — отбросить» к собственному порядку отправки и ведёт `expected_drops_total`. Сервис должен отбросить ровно столько же.

### 4.6 Метрики генератора

`/metrics` на порту 9101: `vq_gen_telemetry_produced_total`, `vq_gen_faults_injected_total{type}`, `vq_gen_expected_drops_total`, `vq_gen_decisions_received_total`, `vq_gen_decisions_applied_total`, `vq_gen_decisions_ignored_total{reason}`, `vq_gen_decision_delay_sim_seconds`, `vq_gen_sim_time_seconds`.

- `vq_gen_decision_delay_sim_seconds` — гистограмма: тик применения рекомендации минус тик входа в зону решения (§4.2 п. 4).
- Метки известных значений (`type`: `dup`, `late`, `outage`; `reason`: `already_serving`, `stale_trip`) заводятся нулями при старте; `reason="invalid"` появляется с первой такой записью.

## 5. Витрина

### 5.1 Живая страница `viewer`

FastAPI 0.142.1 + uvicorn 0.54.0, порт 8000 (на хосте — `VQ_VIEWER_PORT`, §2.2).

- Каждый источник читается своим фоновым потоком со своим таймаутом (1 с); `/api/state` берёт готовые срезы и никогда не ждёт источник. Опрос дольше 1 с помечает источник недоступным (замёрзший Postgres не исполняет и свой `statement_timeout`, а `connect_timeout` libpq не короче 2 с), срез старше 3 с — тоже. Недоступный источник помечается на странице, остальное продолжает обновляться.
- Kafka: `queue.v1` и `decision.v1` с начала, `assign` без группы и коммитов. По каждой станции хранится запись с наибольшим `vq-src-offset`; запись с `vq-src-offset`, не большим уже виденного, — повтор (§2.6). Из `decision.v1` — последние 200 записей с дедупликацией по `(unit_uuid, at)` и итоги по всему логу. Раз в секунду читаются high watermark обоих топиков: это и доступность брокера, и отставание чтения. После `make reset` (offset ушёл назад) кеш топика сбрасывается. Запись не той формы — не JSON-объект (в том числе битый JSON и глубокая вложенность), без заголовка `vq-src-offset` из ASCII-цифр (разбор один с `verify`: `vq.core.codec.parse_src_offset`), без ключей §3.9, с `at` не в формате или вне 2001–2100 — считается в `malformed` и ничего не меняет; типы остальных полей не проверяются: записи пишет наш `dispatcher`.
- Postgres, только чтение: `processor`, `stations`, `vehicles` одной транзакцией `REPEATABLE READ READ ONLY` раз в 0,5 с — согласованный срез на `next_offset`.
- `/metrics` dispatcher (`VQ_DISPATCHER_METRICS` — адрес или несколько через запятую) и генератора; итог прошлого прогона — `/out/summary.json`. Экземпляров dispatcher может быть несколько (основной и `dispatcher-b`, §2.2): витрина опрашивает все и показывает владельца площадки — экземпляр с наибольшим `vq_epoch`, как панели Grafana. Если основной остановлен, а standby ещё не забрал партицию (до `session.timeout.ms`, §2.4), показывается ещё не работавший standby с нулевыми счётчиками (в Grafana панели «сейчас», времени с чекпоинта и датчиков одной партиции в это время пусты: нули до `claim` — не данные); если не отвечает никто — последний удачный срез с пометкой.
- `GET /api/state` — строгий JSON (не конечные числа из любого источника становятся `null`):
  - «сейчас» — `max(processor.now_ts, наибольший at в queue.v1 и decision.v1)`; свежесть машин — от `now_ts` того же среза Postgres (`queue.v1` бывает впереди Postgres на пачку);
  - станции: координаты, число закреплённых машин, занявшая машина с моментами занятия и освобождения, очередь из `queue.v1`;
  - машины: позиция, фаза, цель, своя станция, свежесть;
  - лента решений;
  - здоровье: `epoch`, `next_offset`, `updated_at` и точные счётчики из строки `processor` (принято, отброшено, невалидно); ожидаемые отбросы — из `/metrics` генератора (или `summary.json` после e2e) и их совпадение с отброшенными; решения по типам, точность прогноза, `fsm_resync` (самолечение и конец заезда в радиусе разгрузки) и лаг — из `/metrics` dispatcher (счётчики — с запуска процесса). Точность — число занятий с прогнозом и доля |ошибки| ≤ 5 с по всем занятиям (корзина `le=5` гистограммы `vq_prediction_abs_error_seconds`; критерий — §6.1); квантили и знак ошибки — в Grafana;
  - отметки offset: «очереди — последнее изменение на offset X, карта на offset Y». X — наибольший `vq-src-offset` валидных записей `queue.v1`, то есть сообщение, последним изменившее какую-то очередь; `queue.v1` публикуется только при изменении, поэтому в установившемся режиме X < Y — норма. Y = `processor.next_offset − 1`. Если X > Y (выходы уже отправлены, а чекпоинт ещё нет — разрыв не больше пачки), в конце добавляется «; очереди впереди карты на N».
- `GET /` — `static/index.html` на чистом JS и SVG:
  - карта: станции с кругами 50 м и 1500 м, разгрузка, машины цветом фазы, пунктир к цели у перенаправленных;
  - карточки очередей станций;
  - лента решений и полоса здоровья;
  - опрос `/api/state` раз в 500 мс.
- В `ARCHITECTURE.md` оговаривается, что чтение внутренних таблиц процессора — операторский вид для демо; в продакшене витрина читала бы опубликованные топики или реплику.

### 5.2 Метрики `dispatcher` и Grafana

Счётчики и гистограммы по событиям пачки обновляются после её успешного чекпоинта (§2.4); серии по станциям и известным меткам заводятся нулями при старте.

- `vq_messages_total{result=accepted|invalid|not_newer}` — счётчики процесса, сбрасываются при рестарте; точные значения лежат в `processor` (§2.5).
- `vq_event_time_seconds` («сейчас»), `vq_event_time_lag_seconds` (часы минус «сейчас», считается в момент опроса; осмысленна только в реальном темпе)
- `vq_queue_publications_total{station}`, `vq_queue_length{station}` (при `claim` восстанавливается из `last_published_queue`)
- `vq_decisions_total{result, reason}` (`reason=""` у `recommended`), `vq_decision_gain_seconds` (гистограмма, только `recommended`)
- `vq_prediction_error_seconds` (гистограмма со знаком: фактическое занятие минус предсказанное начало; корзины −300, −120, −60, −30, −10, −5, −1, 0, 1, 5, 10, 30, 60, 120, 300) и `vq_prediction_abs_error_seconds` (модуль; корзины 0, 1, 2, 3, 5, 10, 20, 30, 60, 120, 300 — для p50/p95 и доли ≤ 5 с). У гистограммы с отрицательными корзинами prometheus_client не отдаёт `_sum`, поэтому знак ошибки виден только по корзинам.
- `vq_fsm_resync_total{station}` — самолечение (`station` — станция остановки) и конец заезда «к станции» в радиусе разгрузки (`station` — прежняя цель); при послушном генераторе 0
- `vq_last_checkpoint_unixtime`
- `vq_station_releases_total{station, reason}`
- `vq_batch_seconds`, `vq_checkpoint_seconds` (гистограммы), `vq_consumer_lag_messages`, `vq_epoch`

Датчики одной партиции (`vq_queue_length`, `vq_consumer_lag_messages`, `vq_event_time_lag_seconds`) у экземпляра, потерявшего партицию, остаются от его последней пачки (`vq_event_time_lag_seconds` считается при опросе и растёт), а его `vq_epoch` — прежним; владелец площадки — экземпляр с наибольшим `vq_epoch`.

Grafana: источник Prometheus и дашборд «Виртуальные очереди» подключаются через provisioning, анонимный вход — только чтение. Prometheus (опрос раз в 5 с) собирает `dispatcher:9100` и `dispatcher-b:9100` одним job (пока standby не запущен, его цель — down) и `generator:9101` (генератор e2e из `docker compose run` виден по этому имени только с `--use-aliases`). Дашборд генерируется `tools/gen_dashboard.py` (`--check` сверяет файл с генерацией), JSON руками не правится. Он открывается прямой ссылкой `/d/vq` (её печатает `make up`): домашний дашборд из файла Grafana 13 получает служебный uid, который анонимному зрителю не прочитать. Правила запросов:
- счётчики dispatcher — только через `increase()`/`rate()`: они сбрасываются при рестарте процесса;
- датчики одной партиции — только у экземпляра с наибольшим `vq_epoch`;
- «отброшено = ожидалось» панель показывает двумя приближёнными числами (`increase()` экстраполирует, цели опрашиваются в разные моменты); точное равенство проверяют витрина (по `processor`) и `make e2e`.

Панели:
- состояние: доступность dispatcher и генератора, `epoch`, «сейчас», время с последнего чекпоинта, `fsm_resync` за период;

**Точность прогноза** (`test_closed_loop`, решение 14.10). Занятие спокойное, если предшественники у станции те же, что в момент решения. Каждое спокойное занятие при задержке 0 и 6 с: 0 ≤ ошибка ≤ 2 + 2·L, где 1–2 с — округление ETA и тик остановки, а L — на сколько тиков позже позиции-триггера повернула эта машина или ещё не повернувшая предшественница. У каждого возмущённого занятия есть причина из списка — сведения, которых при решении не было: позже перенаправленная сюда машина приехала раньше; предшественницу увели на другую станцию; несвежая при решении машина (обрыв) оказалась впереди; стоявшая позади въехала в радиус раньше (её ETA отставал не больше чем на 1 + 2·L с). Необъяснённых 0. Доля |ошибка| ≤ 5 с по всем занятиям печатается в итоге pytest и проверяется только как порог регрессии: seed 42 — ≥ 0,85 при 0 с, ≥ 0,80 при 6 с (прототип: 0,924 и 0,840; у спокойных в пределах 5 с — 107 из 107 и 100 из 104). Исходная цель «95 % всех занятий» (в ТЗ порога нет) по правилу ТЗ недостижима (§10).

Итог pytest печатает секцию «цифры прогона»: точность прогноза при задержках 0 и 6 с и наименьший зазор отсчётов генератора до порогов (`test_config`). `test_store_pg.py` на testcontainers (`postgres:18.4-trixie`): миграция идемпотентна и даёт колонки §2.5; сессия — с таймаутами и параметрами TCP §2.4 (`keepalives_*`, `tcp_user_timeout`), в autocommit; `claim` создаёт строку и увеличивает `epoch`; чекпоинт со старым `epoch` отвергается и ничего не меняет; состояние сохраняется и читается побитово (float, `NULL` против `'[]'`, `radius_station` пусто и задано, не-ASCII, порядок строк и повторные upsert, пустое состояние с `now_ts = NULL`); прогон → `claim` из настоящего Postgres → то же сообщение без изменений → ноль выходных записей, дальше — те же выходы; несовпадение `logic_version` или `config_hash` при непустом состоянии — отказ с откатом (`epoch` не растёт), при пустом — версии переписываются; состояние другой площадки или строки `stations`/`vehicles` при пустом `next_offset` — отказ `config_changed`; том со схемой другой версии — отказ `schema_changed` с откатом; замёрзший сервер (`docker pause`): процесс с настоящим store выходит с кодом 1 за срок сторожа (`exit_postgres_stalled`).

### 6.3 Сквозные

`make e2e` и `make e2e-chaos` — `tools/e2e.py`, запускается на хосте (`uv run`) против поднятого стенда. Каждая проверка печатается строкой PASS/FAIL с числами, итог — JSON последней строкой stdout и в `out/e2e.json` (`out/e2e-chaos.json`); код 0, только если прошли все.

- `make e2e`: `make reset UP_PROFILES=` — свежие тома, стенд без демо-генератора (тот писал бы в `telemetry.v1`, и генератор e2e отказался бы стартовать на непустом топике, §4.4). Генератор на переднем плане: `docker compose run --rm --use-aliases -T generator vq-generator --speed 20 --duration 3600 --seed 42` (`--use-aliases` — чтобы Prometheus и витрина видели его по имени `generator`; 182 с, весь `make e2e` вместе со сбросом и `verify` — 3,5–4 минуты); нужны код 0 и `summary.error = null`. Затем high watermark `telemetry.v1` = `summary.produced` (идемпотентный продюсер ничего не потерял и не задвоил); ждём, пока `processor.next_offset` его догонит; `vq-verify` в образе приложения (`docker compose run --rm --no-deps -T dispatcher vq-verify`). Дополнительные проверки:
  - `processor.msgs_not_newer` = `summary.expected_drops`;
  - `summary.decisions.ignored.already_serving` = 0 и `fsm_resync` офлайн-прогона `verify` = 0 (`vq_fsm_resync_total` — счётчик процесса, после рестарта он неполон);
  - есть и `recommended`, и `no_gain`;
  - по офлайн-прогону: инварианты `verify` (ниже) и каждая машина хотя бы раз заняла станцию (полный цикл через разгрузку за час не гарантирован: старт — до 9993 м от станции);
  - `RestartCount` контейнера `dispatcher` не изменился: скрытых падений не было.

  Точные числа и хэши e2e не проверяет: телеметрия замкнутого контура зависит от часов старта и задержек решений.
- `make e2e-chaos`: то же, плюс две аварии `dispatcher`, пока генератор пишет:
  - на 25 % прогона — точка аварии `VQ_CRASH_FILE` (`docker compose exec -T dispatcher touch /tmp/vq-crash`): процесс выходит с кодом 137 после `flush` ближайшей пачки, отправившей хотя бы одну запись, и до её чекпоинта (§2.4), поэтому повтор детерминирован;
  - около 60 % (момент из `random.Random(seed)`, 55–65 % прогона) — `docker compose exec -T dispatcher sh -c 'kill -KILL -1'`: процесс `dispatcher` получает SIGKILL (PID 1 — tini, `init: true`, его `kill -1` не трогает), и контейнер выходит с кодом 137.

  `docker compose kill` не годится: Docker считает его ручной остановкой при любом сигнале, и `restart: unless-stopped` контейнер не поднимает. Проверки сверх e2e: по каждой аварии — код выхода 137, перезапуск политикой, новый `claim` и чекпоинт; `RestartCount` за прогон вырос ровно на 2, `epoch` — не меньше чем на 2; `verify` проходит и показывает повторов не меньше max(1, записей пачки точки аварии), все байт в байт. Время от выхода процесса (`State.FinishedAt`) до старта контейнера, `claim`, нового `epoch` в Postgres (опрос 50 мс) и первого чекпоинта (`updated_at`) — по часам ВМ Docker — печатается таблицей Markdown и идёт в README; числа прототипа — §2.6.
- `make verify` (`vq-verify`, `src/vq/tools/verify.py`, в образе приложения, §2.7): берёт `N = processor.next_offset`; отказывается (код 1 с причиной), если строки `processor` нет, `logic_version` или `config_hash` в ней не совпадают с кодом, low watermark `telemetry.v1` > 0 при `N > 0` (перепрогон с пустого состояния невозможен) или `N` больше high watermark (лог создан заново). Прогоняет `telemetry.v1[0, N)` через `Engine` офлайн с пустого состояния (`assign` партиции 0, без группы и коммитов), помечая каждый выход его `src_offset`; читает `queue.v1` и `decision.v1` целиком и оставляет записи с `vq-src-offset < N`. Записи с одинаковыми `(топик, ключ, vq-src-offset)` — повторы: они обязаны совпадать байт в байт (иначе провал `replay_differs`), считаются и схлопываются. После этого по каждому ключу последовательность в порядке `vq-src-offset` обязана совпасть с офлайн-последовательностью (`missing`, `extra`, `value_differs`). Провал и в случаях: запись без корректного `vq-src-offset` (только ASCII-цифры) — `no_src_offset`; первое появление записи с меньшим `vq-src-offset` после большего по тому же ключу — `reordered` (потребитель по §2.6 отбросил бы её как повтор); два офлайн-выхода с одинаковыми `(топик, ключ, src)` — `offline_duplicate` (§2.3). Кроме того, точные счётчики `processor` (`accepted`, `not_newer`, `invalid`) обязаны совпасть с офлайн-счётчиками, а после каждого сообщения офлайн-прогона — инварианты: занявшая станцию — в фазе `service` с целью, равной этой станции (у станции одна занявшая, машина занимает не больше одной станции); машина — не больше чем в одной строке последних опубликованных очередей. Вывод — строки для человека (первые 10 расхождений подробно, с куском байтов вокруг первого различия) и один JSON последней строкой stdout (его разбирает `make e2e`); код 0 — совпало, 1 — расхождение или сверка невозможна. `min.compaction.lag.ms` сутки гарантирует, что за прогон компакция ничего не удалит.

## 10. Известные ограничения и риски

- **Задержка на станции.** Если машина обслуживается дольше 230 с, станцию передают по таймеру, и прогноз для следующих оптимистичен. ТЗ требует освобождения по таймеру; это же защищает от потерянной телеметрии занявшей.
- **Часы машины спешат.** «Сейчас» уходит вперёд, остальные машины становятся несвежими. Защиты нет (буква ТЗ); нужен watermark или карантин будущих `ts`.
- **Дрожание GPS у границы радиуса.** Пороги строгие, без интерполяции и гистерезиса (§3.11 п. 16): одна точка занявшей в 50 м от станции и дальше — выход: станция освобождается и переходит к ждущей, если она есть, а машина до захода в радиус разгрузки считается «к разгрузке». Генератор такого не создаёт: его позиции точные.
- **Применённые переходы не пересматриваются** (§3.6, §3.11 п. 14). Опоздавший выход занявшей, пришедший после срабатывания таймера, меняет только её фазу: станция остаётся освобождённой по таймеру, а не в момент фактического выезда. Генератор опаздывает только дальше 100 м от станций (§4.5).
- **Опоздание на 230 с и больше.** Сообщение, отстающее от «сейчас» на 230 с и больше, может занять свободную станцию на шаге 5 уже после таймеров шага 4 (§3.4, §3.6); такое занятие переживает свой таймер до следующего учтённого сообщения, которое освободит станцию с тем же `R`. ТЗ ограничивает опоздание 60 с, генератор — тоже.
- **Холодный старт без состояния при непустом топике.** По букве ТЗ первая позиция трактуется как «к станции», и машина, едущая к разгрузке, считается неверно до разгрузки. В радиусе разгрузки заезд заканчивается (§3.5): дальше модель верна, и на подъезде к своей станции будет решение.
- **Пропущенный радиус разгрузки.** Если ни одна точка не попала в радиус 50 м разгрузки, машина остаётся «к разгрузке» (буква ТЗ), а машина, которую модель держит «к станции», не заканчивает заезд (§3.5). Генератор такого не создаёт.
- **Неисполненная рекомендация.** Если генератор не успел исполнить рекомендацию (машина уже начала обслуживание дома, долгий простой dispatcher), модель сходится сама (§3.5). Остановка у фактической станции — самолечение; приезд к занятой станции считается от входа в её радиус, поэтому ждущие сразу стоят в том же порядке, что в мире. Обслуживание, которого модель не увидела, закрывает конец заезда в радиусе разгрузки. До этого машина стоит строкой в очереди рекомендованной станции, и прогноз там пессимистичен. Видно в `vq_fsm_resync_total`.
- **Перезапуск генератора без сброса** не поддерживается: генератор отказывается стартовать на непустом топике. Флаг `--allow-dirty` — на свой риск: модель сходится примерно за цикл, а «отброшено = ожидалось» на витрине после такого рестарта не сходится (§4.4); с ним запускается демо-генератор `make up` (§2.2).
- **Выигрыш считается по ожиданию, а не по времени начала обслуживания.** В примере T4 на S2 начнёт обслуживание на 70 с позже, чем на S1, но правило ТЗ рекомендует S2. Реализовано как в ТЗ, отмечено в README.
- **Точность прогноза.** ТЗ порога точности не задаёт; исходная цель дизайна «|ошибка| ≤ 5 с у 95 % занятий» по правилу ТЗ недостижима. Правило считает ожидание только для решающей машины: поздняя рекомендация на соседнюю станцию (≈ 220 с пути) обгоняет раннюю дальнюю (350–500 с), и прогноз той сдвигается на целое занятие (230 с); на 8 seed в пределах 5 с — 84–92 % всех занятий. Спокойные занятия (предшественники те же, что при решении) точны: 0 ≤ ошибка ≤ 2 + 2·L, в пределах 5 с — 96–100 % на тех же seed (§6.1).
- **Выходы at-least-once.** После падения возможны повторы уже выданных записей, в том числе одинаковые очереди подряд и повтор решения; потребители схлопывают их по `vq-src-offset`, решения — и по `(unit_uuid, at)` (§2.6).
- **Поздние записи зомби и компакция `queue.v1`.** Замороженный процесс после разморозки дописывает свою пачку (байт в байт как новый владелец), но уже после более новых записей тех же станций. Потребители по правилу §2.6 это игнорируют; компакция же хранит последнюю по позиции запись, и если станция больше не публиковалась, текущей останется устаревшая очередь. Лечится следующей публикацией станции; полностью — фенсингом продюсера (транзакции Kafka, §2.8 ответ 5).
- **Перепрогон на другой платформе.** Детерминизм гарантирован для тройки «код + `site.toml` + образ» (§2.7). Отсчёты плеч после рекомендации не защищены зазором от порога 50 м (§4.2): `verify` вне образа приложения может разойтись с процессором в последнем бите гаверсинуса.
- **Брокер — одна нода в dev-container без fsync.** Потеря ноды — потеря данных; гарантии предполагают кластер с RF=3.
- **Standby и штатная остановка.** Static-участник не шлёт LeaveGroup (§2.4), поэтому standby забирает партицию только через `session.timeout.ms` (прототип: 10,6–12,3 с), в том числе после SIGTERM; перезапуск того же контейнера получает её сразу.
- **Один `group.instance.id` у двух процессов.** Они вытесняют друг друга по кругу (`FENCED_INSTANCE_ID` или фенсинг чекпоинта → `exit(1)` → рестарт): данные верны, но `epoch` растёт, а задержка рестарта Docker доходит до 60 с. Поэтому у standby свой id (§2.2), а второй dispatcher, запущенный, например, с хоста, обязан задать свой `VQ_GROUP_INSTANCE_ID`.
- **Отказ старта в цикле.** Отказ старта (`exit(2)`, §2.4) `restart: unless-stopped` повторяет с растущей задержкой Docker, пока не сделан `make reset`; при `log_recreated` и `state_older_than_log` каждая попытка увеличивает `epoch` (водяные знаки проверяются после `claim`). Причину показывают `make up` и `make logs` (строка `start_refused`).
- **Схема без миграций.** `CREATE TABLE IF NOT EXISTS` не меняет существующие таблицы: том от другой схемы — отказ `schema_changed` (§2.5), и смена схемы, как и смена `logic_version` или `config_hash`, требует `make reset`: состояние и лог удаляются вместе.
- **Инкрементальности нет.** Все очереди пересчитываются на каждое сообщение: 40 машин — ≈ 0,3 % одного ядра CPU, 400 машин на тех же 4 станциях — ≈ 600 мкс на сообщение, ≈ 24 % ядра (разовый замер на хосте); предел одного ядра — порядка 700–800 машин на площадку, дальше нужен инкрементальный пересчёт.
- **Одна площадка — одна партиция — одно ядро.** Масштабирование — по площадкам.
