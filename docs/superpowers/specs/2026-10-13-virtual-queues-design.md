## 2. Архитектура

### 2.1 Схема

```
 generator ──telemetry.v1 (1 партиция, key=unit_uuid)──▶ dispatcher ──queue.v1 (compact, key=station_uuid)──▶
     ▲                                                      │  │
     └──────────decision.v1 (key=unit_uuid)─────────────────┘  │ чекпоинт: состояние + offset + epoch,
                                                                │ одна транзакция
                                                                ▼
 viewer :8000 ◀── queue.v1, decision.v1 ──      Postgres: processor / stations / vehicles
        ▲                                                       │
        └────────────── SELECT, только чтение ──────────────────┘

 dispatcher :9100/metrics, generator :9101/metrics ──▶ Prometheus :9090 ──▶ Grafana :3000
 Redpanda Console :8080
```

### 2.3 Топики

| Топик | Партиции | Ключ | Настройки | Назначение |
|---|---|---|---|---|
| `telemetry.v1` | 1 | `unit_uuid` | `cleanup.policy=delete`, `retention.ms=604800000` | вход; источник для перепрогона |
| `queue.v1` | 1 | `station_uuid` | `cleanup.policy=compact`, `min.compaction.lag.ms=86400000` | очередь станции; последняя запись по ключу — текущая очередь; история за сутки сохраняется для `make verify` |
| `decision.v1` | 1 | `unit_uuid` | `cleanup.policy=delete`, `retention.ms=604800000` | решения: команды генератору и аудит |

`dispatcher` при старте проверяет, что у `telemetry.v1` ровно одна партиция, и иначе отказывается работать (детерминизм, §2.7).

Каждая запись `queue.v1` и `decision.v1` несёт заголовок Kafka `vq-src-offset` — offset сообщения `telemetry.v1`, обработка которого её породила (десятичная строка). Payload остаётся ровно по ТЗ; повторы после падения совпадают байт в байт вместе с заголовком. Пара `(station_uuid, vq-src-offset)` уникальна: шаг публикует не больше одной записи на станцию.

### 2.4 Процессор `dispatcher`

Один процесс, обработка в одном потоке; HTTP `/metrics` — в фоновом потоке `prometheus_client.start_http_server`.

**Клиенты** (`confluent-kafka` 2.15.1):

- consumer: `group.id=dispatcher`, `group.instance.id=dispatcher-<site_id>` (static membership: перезапущенный контейнер возвращает себе партицию без ожидания таймаута; поддержку в Redpanda v26.2 проверить первым шагом реализации, без неё — только таймауты ниже), `session.timeout.ms=10000`, `heartbeat.interval.ms=3000`, `enable.auto.commit=false`, `auto.offset.reset=error`, `group.protocol=classic`, `partition.assignment.strategy=range`;
- producer: `enable.idempotence=true`, `acks=all`, `linger.ms=5`, `compression.type=zstd`, `message.timeout.ms=30000`.

**Получение партиции** (`on_assign`, вызывается внутри `consume()`):

1. `store.claim(site_id)` — одна транзакция Postgres, строго в таком порядке: `INSERT INTO processor … ON CONFLICT DO NOTHING`; `UPDATE processor SET epoch = epoch + 1 WHERE site_id = … RETURNING epoch, next_offset, now_ts, logic_version, config_hash, счётчики`; проверка версий по `RETURNING` (§2.5); `SELECT` станций и машин с `ORDER BY` по ключу. Отдельного `SELECT processor` до `UPDATE` нет: строка блокируется `UPDATE`, поэтому параллельный `claim` и чекпоинт сериализуются.
2. Если `next_offset` задан, проверить `low ≤ next_offset ≤ high` по `get_watermark_offsets`. Иначе отказ старта (`state_older_than_log` или `log_recreated`) с подсказкой `make reset`; так же обрабатывается `ERR__AUTO_OFFSET_RESET`.
3. Собрать `Engine` из прочитанного состояния.
4. `assign` партиции с offset = `next_offset`, а если состояния ещё нет — явно `OFFSET_BEGINNING`.

**Потеря партиции** (`on_revoke`, `on_lost`): выбросить `Engine` из памяти и не обрабатывать сообщения до следующего назначения. Сообщения, полученные до смены назначения, отбрасываются: перед применением первого сообщения пачки проверяется, что его offset равен ожидаемому (`next_offset` из `claim` или конец предыдущей пачки); иначе пачка отбрасывается и чтение переставляется на ожидаемый offset.

**Цикл:**

1. `consume(num_messages=500, timeout=0.25)`.
2. Каждое сообщение по одному: `engine.apply(value)` возвращает выходы и события.
3. Отправить выходы в порядке появления, с заголовком `vq-src-offset`, затем `flush(timeout=10)`. Если в очереди что-то осталось или пришла ошибка доставки — `exit(1)`.
4. Чекпоинт, одна транзакция Postgres за один round-trip: `UPDATE processor SET next_offset, now_ts, счётчики, updated_at WHERE site_id = … AND epoch = мой`; если затронуто 0 строк, партицию забрал другой экземпляр — `exit(1)`; иначе пакетный upsert 4 станций и до 40 машин (`INSERT … SELECT FROM unnest(...) ON CONFLICT DO UPDATE` или pipeline psycopg); `COMMIT`.
5. `consumer.commit(offset, asynchronous=True)` — только чтобы Console и метрики видели лаг. Источник правды для offset — Postgres.
6. Обновить метрики по событиям пачки.

**Ошибки — crash-only, но не на каждый чих.** `exit(1)` — при фатальной ошибке Kafka (`KafkaError.fatal()`), ошибке доставки, фенсинге, любой ошибке или таймауте Postgres и при исключении в ядре. Информационные ошибки `consume()` (`_TRANSPORT`, `_ALL_BROKERS_DOWN`, `_PARTITION_EOF`) только логируются: librdkafka переподключается сам. Перед `exit(1)` и по SIGTERM вызывается `consumer.close()` (LeaveGroup). Невалидное сообщение ошибкой не считается (§3.4), а ядро обязано не бросать исключений ни на каком входе (§6.1) — иначе одно сообщение остановило бы поток навсегда.

**Postgres:** DSN с `connect_timeout=5`, `keepalives_idle=5` и `options='-c statement_timeout=5000 -c lock_timeout=2000 -c idle_in_transaction_session_timeout=10000'`.

**Логи:** JSON в stdout с полями `site`, `epoch`, `offset`, `event`. Строки INFO — на `claim`, потерю партиции, фенсинг, отказ старта и на каждое решение (ожидание и ETA по всем станциям, выбор, выигрыш). `unit_uuid` — только в логах, не в метках метрик.

Порядок «сначала выходы, потом чекпоинт» гарантирует, что выходы не теряются: падение между `flush` и `COMMIT` приводит к повторной обработке пачки и повторной отправке тех же записей.

### 2.5 Состояние в Postgres

`migrations/001_state.sql`, применяется `dispatcher` при старте (`CREATE TABLE IF NOT EXISTS`):

```sql
CREATE TABLE IF NOT EXISTS processor (
  site_id        text PRIMARY KEY,
  epoch          bigint NOT NULL,
  next_offset    bigint,                -- NULL: ещё ничего не обработано
  now_ts         bigint,                -- «сейчас», секунды epoch
  logic_version  text   NOT NULL,
  config_hash    text   NOT NULL,
  msgs_accepted  bigint NOT NULL DEFAULT 0,  -- счётчики пишутся в чекпоинте вместе с offset:
  msgs_not_newer bigint NOT NULL DEFAULT 0,  -- точные (не сбрасываются при рестарте), их
  msgs_invalid   bigint NOT NULL DEFAULT 0,  -- сравнивают e2e и витрина
  updated_at     timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE IF NOT EXISTS stations (
  station_uuid          text PRIMARY KEY,
  occupant_uuid         text,
  occupied_at           bigint,
  last_release_at       bigint,
  last_published_queue  text,           -- канонический JSON строк последней опубликованной очереди; NULL — ещё не публиковалась
  updated_at            timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE IF NOT EXISTS vehicles (
  unit_uuid          text PRIMARY KEY,
  home_station       text    NOT NULL,
  last_ts            bigint  NOT NULL,
  lat                double precision NOT NULL,
  lon                double precision NOT NULL,
  speed_kmh          double precision NOT NULL,
  phase              text    NOT NULL,  -- to_station | waiting | service | served | to_dump
  target_station     text    NOT NULL,
  radius_entered_at  bigint,            -- вход в радиус целевой станции на этом подъезде
  arrived_at         bigint,            -- приезд, от которого считается wait_seconds
  dump_visited       boolean NOT NULL,  -- была в радиусе разгрузки на этом плече
  decided            boolean NOT NULL,  -- рекомендация в этом заезде уже считалась
  predicted_start    bigint,            -- service_start, предсказанный при решении (метрика точности)
  updated_at         timestamptz NOT NULL DEFAULT now()
);
```

- Поля строк один к одному соответствуют модели ядра (§3.3). `updated_at` — служебное поле для витрины, в расчёте не участвует.
- `logic_version` — константа в коде, меняется вместе с правилами. `config_hash` — sha256 канонизированного `site.toml`. Если они не совпали, а состояние непустое, `dispatcher` отказывается стартовать и подсказывает `make reset`.
- Пишет только `dispatcher`; `viewer` и Grafana только читают.
- Чекпоинт пишет все строки (4 станции и до 40 машин), без отслеживания изменённых.
- `last_published_queue` — `text`, а не `jsonb`: `jsonb` переставляет ключи и нормализует значения, а сравнение (§3.9) идёт по байтам. Хранится ровно та сериализация строк, что уходит в топик (без `at`); `NULL` (не публиковалась) и `'[]'` (опубликована пустая) различаются.
- Числа: времена — `bigint`, координаты и скорость — `double precision` (точный круг для float64), флаги — `boolean`. Загрузка обязана восстановить состояние побитово; это проверяет интеграционный тест (§6.2).

### 2.6 Гарантии и рестарт

- Состояние и offset атомарны: после рестарта нет ни потерянных, ни дважды применённых сообщений.
- Выходы at-least-once. Сообщения после последнего чекпоинта обрабатываются повторно и дают байт в байт те же записи: ядро детерминировано, `at` — время событий.
- Правило для потребителей: текущая очередь станции — запись с наибольшим `vq-src-offset`; запись с `vq-src-offset`, не большим уже виденного, — повтор и игнорируется. Решения дедуплицируются по `(unit_uuid, at)` — эта пара уникальна, так как решение по машине одно на заезд. Правило «наибольший `at`» не годится: за одну секунду очередь станции может публиковаться несколько раз с одним `at`.
- Это прямое отступление от «одинаковые подряд очереди не публикуются»: после падения хвост до одной пачки (≤ 500 входных сообщений) публикуется повторно, и в логе могут оказаться одинаковые записи подряд. Потребитель схлопывает их по `vq-src-offset` (§3.11).
- Зомби — процесс, потерявший партицию, но ещё работающий, — не может записать чекпоинт из-за условия `epoch = мой`. Выходы, которые он успел отправить, совпадают с теми, что отправит новый владелец.
- **Время восстановления** = рестарт контейнера (~1 с) + возврат партиции группой + `claim` (одна транзакция на 45 строк, миллисекунды, от длины лога не зависит) + повтор не больше одной пачки. Со static membership перезапущенный процесс получает партицию сразу; standby перехватывает её через `session.timeout.ms` (10 с); без этих настроек после `kill -9` это было бы до 45 с (умолчание librdkafka). Фактическое число измеряет `make e2e-chaos` и попадает в README.
- Решения, выданные в окне восстановления, опаздывают, но не теряются; генератор исполняет их, пока машина не начала обслуживание (§4.3), а если не успел — модель сходится сама (§3.5, самолечение).
- Полный перепрогон (`make reset` и та же телеметрия) воспроизводит те же записи; он корректен только для той же `logic_version` — это и есть `make verify`.
- Стенд — одна нода Redpanda с RF=1 в режиме dev-container (без fsync): потеря ноды — потеря данных с любым брокером. В продакшене RF=3, `acks=all`, `min.insync.replicas=2`. Оговорка — в README.

### 2.7 Детерминизм

Выходы — чистая функция последовательности сообщений `telemetry.v1` в порядке лога:

- одна партиция — один полный порядок;
- «сейчас» берётся из `ts` в payload; timestamp записи Kafka не используется;
- ETA отсчитывается от `ts` позиции машины, а не от «сейчас»;
- арифметика в целых секундах, одно округление на длительность (§3.2);
- нет часов компьютера, таймеров, случайности, итерации по неупорядоченным множествам;
- сообщения применяются по одному, поэтому границы пачек не влияют на результат.

Следствие: запись `telemetry.v1`, прогнанная через ядро офлайн с любой скоростью, даёт те же `queue.v1` и `decision.v1`. Это проверяет `make verify` (§6.3).

Детерминизм гарантирован для тройки «код + `site.toml` + образ» (версия Python и libm влияют на последний бит гаверсинуса). Поэтому `make verify` и `make bench` запускаются в образе приложения (`docker compose run --rm dispatcher vq-verify`).

### 2.8 Ответы для `ARCHITECTURE.md` (черновик)

1. **Сколько процессоров и критерий.** Один — `dispatcher`; генератор и витрина процессорами не являются: первый — источник данных, вторая только читает результаты. Критерий: *отдельный процессор выделяется там, где меняется домен согласованности — состояние, которое нужно читать и менять атомарно и в едином порядке событий; очереди, решения и «сейчас» — один домен (площадка), поэтому процессор один.*
2. **Ключ и состояние.** Логический ключ — площадка; физически это единственная партиция `telemetry.v1`. Состояние в Postgres: машины (позиция, фаза, цель, вход в радиус, приезд, флаг решения), станции (занявшая машина, момент занятия, последнее освобождение, последняя опубликованная очередь), «сейчас», offset, `epoch`.
3. **Машины, станции и решение.** Перекладываем всё на ключ площадки: одна партиция даёт всю площадку в едином порядке, и телеметрия по машинам, очереди по станциям и решение считаются в одном процессе над общим состоянием. Решение читает очереди всех станций и в том же шаге переносит машину между двумя очередями, поэтому следующая машина видит результат и две машины не отправляются на одну свободную станцию. Ключ входных сообщений остаётся `unit_uuid` по контракту; партиционирование — по площадке.
4. **Партиции и параллелизм.** `telemetry.v1` — одна партиция на площадку. Ключ `unit_uuid` задан контрактом, и стандартный партиционер разнёс бы машины одной площадки по разным партициям; поэтому при N площадках либо продюсеры телеметрии используют партиционер по площадке (машина → площадка из справочника), либо — если вход внешний и его не изменить — перед процессором ставится маленький этап-секвенсор: он читает многопартиционный вход и перекладывает каждую машину в партицию её площадки, а детерминизм отсчитывается уже от этого топика. `queue.v1` и `decision.v1` — по одной партиции: порядок по ключу сохраняется при любом числе, потребителей мало. Реплик `dispatcher` может быть несколько, активна одна на партицию; каждая смена состава группы — ребаланс, поэтому standby в compose по умолчанию не запущен. Параллелизм ограничен числом площадок: глобальное «сейчас» и решение по всем станциям требуют единого порядка. Внутри площадки узкое место при росте — пересчёт всех очередей на каждое сообщение (O(машин) на сообщение, O(машин²) в секунду); при ×10 машин нужен инкрементальный пересчёт. Цифры: 40 сообщений/с ≈ 6 КБ/с входа, ~4 транзакции чекпоинта в секунду; время на сообщение даёт `make bench` (§6.4).
5. **Гарантии доставки.** Транзакционность нужна там, где два изменения обязаны быть атомарными: состояние и offset — одна транзакция Postgres, иначе рестарт либо теряет, либо дважды применяет сообщения. Для выходов достаточно идемпотентности: выход — детерминированная функция входа, повтор после падения — та же запись с тем же `vq-src-offset`; текущая очередь станции — запись с наибольшим `vq-src-offset`; `decision.v1` дедуплицируется по `(unit_uuid, at)`. Цена названа честно: после падения возможны одинаковые записи подряд (отступление от ТЗ, §3.11). Альтернатива — Kafka-транзакции со снимком состояния в compacted-топике в той же транзакции: выходы exactly-once и одна система, но больше подводных камней (LSO, compaction транзакционных топиков, таймауты транзакций) и нет SQL-доступа к состоянию. Переходить на неё стоит, когда появится потребитель решений без дедупликации.
6. **Рестарт.** Состояние читается из Postgres одной транзакцией — миллисекунды, от длины лога не зависит. Полное время — по §2.6: рестарт контейнера, возврат партиции (сразу со static membership, до 10 с для standby), повтор не больше одной пачки; измеренное `make e2e-chaos` число — в README. Сообщения после последнего чекпоинта обрабатываются повторно и дают те же записи; потребители отбрасывают повторы по правилу из ответа 5, генератор — по `(unit_uuid, at)` и по заезду. Полный перепрогон топика той же версией логики воспроизводит все записи байт в байт.
7. **Что не выносили.** (а) Дедупликацию и определение фазы по машинам с ключом `unit_uuid` — им нужен глобальный «сейчас», а лишний топик добавляет задержку и вторую границу согласованности. (б) Очереди по станциям — решение меняет состав очередей; разделение даёт цикл через Kafka и гонки решений. (в) Само решение — ему нужно атомарно читать все очереди и менять две. Вынесена только витрина: она лишь читает.

## 3. Ядро расчёта

`src/vq/core` — чистый код: без I/O, часов, случайности и сторонних зависимостей.

### 3.1 Конфигурация

`config/site.toml` — общий для сервиса и генератора:

- `site.id`;
- `dump` — координаты точки разгрузки;
- `stations` — четыре станции: `uuid`, `lat`, `lon`;
- `assignment` — закрепление 40 машин за станциями;
- `constants`: обслуживание 200 с, манёвр 30 с (занятие 230 с), расчётная скорость 10 м/с, радиус 50 м, порог «стоит» 1 км/ч, радиус решения 1500 м, горизонт 1800 с, свежесть 30 с, минимальный выигрыш 60 с.

Проверки при загрузке: радиусы 50 м станций и разгрузки не пересекаются; разгрузка дальше 1550 м от каждой станции; каждая машина закреплена ровно за одной станцией.

### 3.2 Время, расстояние, формат

- Время — целые секунды epoch. `ts` должен быть целым числом (допускается float с целым значением), иначе сообщение невалидно.
- Расстояние — формула гаверсинусов, R = 6 371 008,8 м («по прямой между координатами»).
- Время пути на `d` метров: `rhu(d / 10)`, где `rhu(x) = floor(x + 0.5)` — округление половины вверх. Встроенный `round()` банковский и не используется. Для машины «к разгрузке» оба плеча складываются и сумма округляется один раз.
- Пороги строгие: «в радиусе» — `d < 50`, «стоит» — `speed_kmh < 1`, зона решения — `d < 1500`. Ровно 50 м — снаружи.
- Время на выходе — `YYYY-MM-DDTHH:MM:SSZ`, UTC.

### 3.3 Модель

**Машина** (`Vehicle`): `unit_uuid`, `home`, `last_ts`, `lat`, `lon`, `speed_kmh`, `phase`, `target`, `radius_entered_at`, `arrived_at`, `dump_visited`, `decided`, `predicted_start`.

| Фаза | Смысл | Состояние по ТЗ |
|---|---|---|
| `to_station` | едет к целевой станции | к станции |
| `waiting` | стоит в радиусе целевой станции, занятой другой машиной | на станции |
| `service` | занимает целевую станцию | на станции |
| `served` | освобождена таймером, но ещё в радиусе | — (наша) |
| `to_dump` | вышла из радиуса станции после обслуживания | к разгрузке |

Целевая станция (`target`) — своя (`home`), а после рекомендации — рекомендованная, до конца заезда.

**Станция** (`Station`): `uuid`, `occupant`, `occupied_at`, `last_release_at`, `last_published` (строки последней опубликованной очереди).

**Площадка** (`Site`): `now` (`None` до первого учтённого сообщения), машины, станции.

Машина свежая, если `now − last_ts ≤ 30`.

### 3.4 Обработка одного сообщения

`Engine.apply(raw: bytes) -> StepResult(outputs, events)`. Шаги строго по порядку:

1. **Разбор.** JSON-объект с полями `unit_uuid` (строка), `ts` (целое), `lat`, `lon`, `speed_kmh` (числа; `bool` числом не считается); `unit_uuid` есть в конфигурации. `json.loads` с запретом `NaN`/`Infinity`; все числа конечные; `|lat| ≤ 90`, `|lon| ≤ 180`, `0 ≤ speed_kmh < 300`; `ts` в диапазоне 2001–2100 (`1 000 000 000 ≤ ts < 4 102 444 800`) — это ловит миллисекунды и не зависит от «сейчас»; float-`ts` с целым значением приводится к `int`. Иначе — событие `invalid`, состояние не меняется.
2. **Дубли и порядок.** Если у машины уже есть учтённое сообщение и `ts ≤ last_ts` — событие `not_newer`, состояние не меняется. Опоздавшее, но более новое сообщение учитывается.
3. **«Сейчас».** `now = max(now, ts)`.
4. **Таймеры.** Пока есть станция с `occupied_at + 230 ≤ now`: выбрать станцию с наименьшим `R = occupied_at + 230` (при равенстве — по `station_uuid`), освободить по таймеру и передать (§3.6).
5. **Переход машины** по сообщению (§3.5). Может занять или освободить станцию.
6. **Рекомендация**, если сработал триггер (§3.8).
7. **Очереди** всех станций пересчитываются на `now`, изменившиеся публикуются (§3.9).

Невалидные и не новые сообщения не дают выходов и не двигают «сейчас».

### 3.5 Переходы машины

Обозначения для текущего сообщения: `T` — целевая станция машины; `inT` — расстояние до `T` меньше 50 м; `stopped` — `speed_kmh < 1`; `inDump` — расстояние до разгрузки меньше 50 м. Позиция, скорость и `last_ts` обновляются всегда.

Первое учтённое сообщение машины создаёт её с `target = home`, `decided = false`, `phase = to_station`, а затем применяются строки для `to_station`. Поэтому машина, которая с первого сообщения стоит в радиусе своей станции, сразу занимает её или встаёт ждать.

| Фаза | Условие | Действие |
|---|---|---|
| `to_station` | `stopped`, не `inT`, в радиусе 50 м станции `Y ≠ T` | **самолечение:** `target = Y`, `radius_entered_at = пусто`, событие `fsm_resync`; дальше строка ниже применяется уже к `Y`. Нового решения нет (`decided` не меняется) |
| `to_station` | `inT` | если `radius_entered_at` пусто — `radius_entered_at = ts`; затем, если `stopped`: станция `T` свободна → **занятие** в `ts` с `arrived_at = ts`; занята → `phase = waiting`, `arrived_at = radius_entered_at` |
| `to_station` | не `inT` | `radius_entered_at = пусто` |
| `waiting` | `inT`, `stopped`, станция `T` свободна | **занятие** в `ts`, `arrived_at` не меняется |
| `waiting` | не `inT` | уехала необслуженной: `phase = to_station`, `radius_entered_at = arrived_at = пусто` |
| `service` | не `inT` | **освобождение** `T` по выходу в момент `ts` и передача (§3.6); затем «конец заезда» |
| `served` | не `inT` | «конец заезда» (станция уже освобождена таймером) |
| `to_dump` | `inDump` | `dump_visited = true` |
| `to_dump` | не `inDump`, `dump_visited` | `phase = to_station`, `dump_visited = false`, `radius_entered_at = пусто` |

«Конец заезда»: `phase = to_dump`, `target = home`, `decided = false`, `dump_visited = false`, `radius_entered_at = arrived_at = пусто`.

Остальные сочетания ничего не меняют. Проезд через радиус любой станции на скорости ничего не значит. Остановка у нецелевой станции в фазе «к станции» значит приезд к ней (самолечение, решение 14.10): так модель сходится с миром, если рекомендация не была исполнена — опоздала, потерялась или генератор перезапустился. С послушным генератором самолечение не срабатывает, и выходы не меняются; срабатывания видны в метрике `vq_fsm_resync_total`. На фазы `waiting`, `service`, `served` и `to_dump` правило не распространяется.

### 3.6 Занятие, освобождение, передача

- **Занятие** станции `S` машиной `v` по сообщению с `ts`: момент занятия `t = max(ts, S.last_release_at)`; при передаче — `t = max(R, v.arrived_at)`. Так опоздавшие сообщения не дают перекрывающихся занятий и отрицательного ожидания (§3.11). Дальше `S.occupant = v`, `S.occupied_at = t`, `v.phase = service`. Если у `v` задан `predicted_start` — событие `prediction_error = t − predicted_start`, затем `predicted_start = пусто`.
- **Освобождение** в момент `R`: по таймеру `R = occupied_at + 230`, по выходу `R = ts` первого сообщения занявшей машины вне радиуса (выход всегда раньше таймера, иначе таймер уже сработал на шаге 4). `S.occupant = пусто`, `S.last_release_at = R`; при таймере занявшая получает `phase = served`.
- **Передача** сразу после освобождения. Кандидаты — машины с `phase = waiting` и `target = S`, свежие на `now` и стоящие (`speed_kmh < 1`) в последнем учтённом сообщении. Станция переходит к минимальной по `(arrived_at, unit_uuid)`, момент занятия — `R`. Если кандидатов нет, станция свободна, и её займёт первое учтённое сообщение машины, стоящей в радиусе (правило 1 буквально).
- Применённые переходы не пересматриваются: запоздавший выход занявшей машины после срабатывания таймера меняет только её собственную фазу.

### 3.7 Очередь станции

Строки очереди станции `S` на момент `now`:

1. **Занявшая** `o` — всегда, даже если она несвежая: `eta = null`, `service_start = occupied_at`, `free_at = occupied_at + 230`, `wait_seconds = occupied_at − o.arrived_at`.
2. **Кандидаты** — только свежие машины, кроме занявшей:
   - `waiting` с `target = S`: приезд `a = arrived_at`, `eta = null`, вид 0;
   - `to_station` с `target = S`: `eta = last_ts + rhu(dist(позиция, S) / 10)`, `a = eta`, вид 1;
   - `to_dump` с `home = S`: пока `dump_visited = false` — `eta = last_ts + rhu((dist(позиция, разгрузка) + dist(разгрузка, S)) / 10)`; после захода в радиус разгрузки (разгрузка мгновенная) — `eta = last_ts + rhu(dist(позиция, S) / 10)`; `a = eta`, вид 1.

   Кандидат с `eta > now + 1800` в очередь не попадает.
3. **Порядок** кандидатов — по `(a, вид, unit_uuid)`.
4. **Цепочка.** Начало `prev` — `free_at` занявшей, а если её нет — `S.last_release_at` (или −∞). Для каждого кандидата: `service_start = max(a, prev)`, `free_at = service_start + 230`, `wait_seconds = service_start − a`, `prev = free_at`.

Строка очереди: `{"unit_uuid", "eta", "service_start", "free_at", "wait_seconds"}`. Машины в фазе `served` ни в какую очередь не попадают; каждая машина — не более чем в одной очереди и одной строкой.

### 3.8 Рекомендация

**Триггер:** после шага 5 машина в фазе `to_station`, `decided = false` и `dist(позиция, home) < 1500`. Тогда `decided = true` и:

1. Если `now − ts > 30` — отказ `stale_telemetry`.
2. Иначе для каждой станции `X`:
   - `eta_X = ts + rhu(dist(позиция, X) / 10)`;
   - строки очереди `X` по §3.7, но без этой машины;
   - ключ машины — `(eta_X, 1, unit_uuid)`; предшественник — последняя строка с меньшим ключом (занявшая всегда раньше);
   - `prev` — `free_at` предшественника, а если его нет — начало цепочки из §3.7 п. 4;
   - `wait_X = max(0, prev − eta_X)`.
3. Выбор `X*` — минимум по `(wait_X, X ≠ home, dist(позиция, X), X)`.
4. `gain = wait_home − wait_X*`. Если `X* = home` или `gain < 60` — отказ `no_gain`. Иначе — `recommended`: `target = X*`, `radius_entered_at = пусто`.
5. Для метрики точности: `predicted_start = eta_X* + wait_X*` при `recommended`, `eta_home + wait_home` при `no_gain`.
6. Выход `decision.v1` с `at = now`.

Решения принимаются строго в порядке лога и сразу меняют состояние, поэтому решение следующей машины видит перенаправленные раньше.

### 3.9 Публикация и форматы

После шага 6 очередь каждой станции строится заново (станции — в порядке `station_uuid`). Если её строки отличаются от `last_published`, выдаётся запись `queue.v1` с `at = now`, и `last_published` обновляется. Сравниваются только строки; `at` в сравнении не участвует. Пустая очередь `[]` тоже публикуется. При первом расчёте (`last_published` пусто) очередь публикуется как исходная.

Внутри шага сначала идёт решение, затем очереди. Каждая запись несёт заголовок `vq-src-offset` (§2.3). Сериализация — `json.dumps(obj, separators=(",", ":"), ensure_ascii=False)`, ключи в порядке ТЗ, значение в UTF-8. Ключ записи — `station_uuid` для очереди и `unit_uuid` для решения.

```json
{"station_uuid":"S1","at":"2026-09-15T12:00:00Z","queue":[{"unit_uuid":"T1","eta":null,"service_start":"2026-09-15T11:59:00Z","free_at":"2026-09-15T12:02:50Z","wait_seconds":0}]}
{"unit_uuid":"T4","at":"2026-09-15T12:00:00Z","result":"recommended","from_station":"S1","to_station":"S2","gain_seconds":80}
{"unit_uuid":"T4","at":"2026-09-15T12:00:00Z","result":"rejected","reason":"no_gain"}
```

### 3.10 События ядра

`accepted`, `invalid`, `not_newer`, `fsm_resync{station}`, `occupied{station, how=arrival|handover}`, `released{station, reason=timer|exit}`, `decision{result, reason, gain}`, `prediction_error{seconds}`, `queue_published{station}`. Ядро только возвращает события; счётчики ведёт `dispatcher` после успешного чекпоинта.

### 3.11 Трактовки ТЗ

Эта таблица переходит в README. Тип: **отступление** — делаем не как написано; **трактовка** — ТЗ молчит или неоднозначно; **наше** — добавлено сверх ТЗ. На каждую строку есть тест.

| № | Тема | Тип | Решение | Почему |
|---|---|---|---|---|
| 1 | Передача станции | отступление | В момент освобождения станция переходит к первой по очереди свежей стоящей ждущей машине; момент занятия = момент освобождения | По букве правила 1 станцию берёт тот, чьё сообщение первым пришло после освобождения, — это порядок лога, а не приезда. Правило очереди («по времени приезда») и генератор («соблюдают очередь») требуют FIFO |
| 2 | Повторное занятие | наше | Машина, освобождённая таймером и ещё стоящая в радиусе, не занимает станцию снова и не стоит в очередях | Иначе по букве правила 1 она заняла бы станцию в ту же секунду, и таймер потерял бы смысл |
| 3 | Какая станция «на станции» | трактовка | Целевая: своя, после рекомендации — рекомендованная. Остановка «к станции» в радиусе другой станции — приезд к ней (самолечение); проезд на скорости ничего не значит | Таблица состояний не говорит, у какой станции; в примере T4 обслуживается у S2. Без самолечения неисполненная рекомендация навсегда оставляла бы машину «фантомом» в чужой очереди |
| 4 | Ожидание ждущей | трактовка | Ждущая в радиусе: `eta = null`, приезд = вход в радиус; набранное ожидание сохраняется и после занятия | `null` положен «машине, которая уже на станции», а стоящая в радиусе — на станции; ожидание = начало обслуживания − приезд |
| 5 | Отсчёт ETA | трактовка | ETA = `ts` последней позиции + время пути, а не «сейчас» + время пути | ТЗ даёт только длительность. ## 4. Генератор

### 4.1 Площадка

- Разгрузка — `49.1288, 142.6601` (координаты из образца в ТЗ).
- Станции S1–S4 — ровно 10 000 м от разгрузки по азимутам 0°, 10°, 20°, 30°. Соседние станции — около 1 743 м друг от друга, S1–S4 — около 5 176 м. Координаты считает `tools/make_site.py` (точка по азимуту и дальности на сфере); результат записан в `site.toml`.
- Закрепление: S1 — 13 машин (`T-01`…`T-13`), S2 — 11, S3 — 9, S4 — 7. Нагрузка ρ = n·230 / (230 + 2000) ≈ 1,34 / 1,13 / 0,93 / 0,72: S1 перегружена, S4 недогружена, поэтому будут и живые очереди, и смесь `recommended` и `no_gain`.
- Тест конфигурации: проверки из §3.1, плюс маршруты разгрузка↔станция проходят не ближе 100 м к чужим станциям.

### 4.2 Симуляция

`src/vq/generator/sim.py` — чистый код без Kafka (его же использует тест замкнутого контура). Тик — 1 секунда симуляции; на каждом тике каждая машина даёт одно сообщение.

Состояния машины: `drive` (отрезок к точке станции или разгрузки), `arrived`, `queued`, `serving`, `maneuver`. Станция хранит занявшую машину со временем начала и FIFO ждущих по `(radius_entered_at, unit_uuid)` — тот же ключ, что у ядра (§3.6).

Тик `t`:

1. Применить полученные рекомендации (§4.3).
2. Станции: если у занявшей `start + 230 ≤ t`, станция свободна; свободная станция с непустой FIFO передаётся голове очереди со `start = t`.
3. Машины, по `unit_uuid`:
   - `drive`: шаг `min(10 м, остаток)` по дуге большого круга, `speed_kmh = max(шаг × 3,6, 1,0)` (на коротком последнем шаге машина не должна выглядеть стоящей раньше, чем генератор считает её прибывшей). При первом входе в радиус 50 м целевой станции запоминается `radius_entered_at`. Достигнув точки станции — `arrived`. Достигнув разгрузки — мгновенная разгрузка и новый отрезок к своей станции.
   - `arrived` (тик после прибытия, скорость 0): станция свободна и FIFO пуста — `serving` со `start = t`; иначе — `queued`.
   - `queued`: стоит в точке станции, скорость 0.
   - `serving`: стоит до `start + 199`. С `start + 200` — `maneuver`: отъезд в сторону разгрузки на 1,7 м/с (6,12 км/ч), на тике `start + 200 + k` машина в `1,7·k` м от точки станции. На `start + 230` она в 51 м, вне радиуса; дальше `drive` к разгрузке на 10 м/с.
4. Зона решения (только для метрики задержки): машина в `drive` к своей станции, не перенаправленная в этом заезде, впервые ближе 1500 м — `zone_entered_at = t`.
5. Сообщения тика уходят в инжектор сбоев (§4.5), затем в `telemetry.v1`.

Все пороги генератора (зона 1500 м, радиус 50 м станции и разгрузки) считаются `vq.geo.haversine` от тех же float, что уходят в сообщение; `lat`/`lon` пишутся с полной точностью (`repr(float)`), без округления до 4 знаков, как в образце ТЗ. Геометрия подобрана так, что отсчёты не попадают на пороги: длины плеч кратны 10 м, а старт сдвинут на 3 м (§4.4), поэтому отсчёты лежат в 3 м от порогов 50 и 1500 м и далеко от точек округления `rhu`. `test_config` проверяет этот зазор для всех отсчётов.

Так прогноз сервиса совпадает с «реальностью»: освобождение по таймеру и выезд из радиуса приходятся на одну секунду, а передача у генератора и у сервиса идёт по одному ключу.

### 4.3 Рекомендации

- Отдельный поток читает `decision.v1`: `assign` партиции 0 с offset, равным high watermark на момент старта, — до первого тика.
- Повторы отсеиваются по `(unit_uuid, at)`.
- `recommended` применяется, если в этом заезде машина ещё не начала обслуживание (`drive` к своей станции, `arrived` или `queued` у неё), ещё не перенаправлена и `at ≥ trip_started_at` (тик разгрузки; для первого заезда — тик старта). Машина в `queued` удаляется из FIFO своей станции. Новый отрезок — от текущей позиции к точке рекомендованной станции, `redirected = true`. Иначе — счётчик проигнорированных с причиной `already_serving` или `stale_trip`. Если машина всё же не успела, модель сходится сама (самолечение, §3.5).
- После обслуживания и разгрузки машина снова едет к своей станции: `redirected = false`, `zone_entered_at = пусто`, `trip_started_at = t`.
- Синхронного ожидания нет. При ускорении ×N поворот запаздывает на «задержка обработки × N» секунд симуляции; это видно в метрике `decision_delay_sim_seconds`. Замкнутый контур рассчитан на ускорение до ×20, на нём идёт e2e. `--speed max` — только вместе с `--no-decisions`, для записи датасетов под `bench` и `verify`; такая телеметрия не является сценарием замкнутого контура.

### 4.4 Темп, старт, остановка

- `--speed 1|N|max`: тик `k` уходит в момент `start_wall + k / N`; `max` — без пауз.
- Генератор стартует только на пустом `telemetry.v1`, иначе отказывается с подсказкой `make reset`: новая смена с новыми позициями противоречила бы фазам, сохранённым в `dispatcher`. Флаг `--allow-dirty` — для демо, с предупреждением в логе; тогда часы стартуют с `max(текущее время, максимальный ts за последние 1000 записей + 1)` — не по последней записи, потому что в хвосте лежат дубли и опоздания со старыми `ts`. Без флага часы стартуют с текущего времени.
- Старт машин: на отрезке от разгрузки к своей станции, на расстоянии `1603 + 10·k` м от станции, `k` — случайное из `{0…839}` по seed; все едут к станции и передают с первого тика.
- Продюсер: `enable.idempotence=true`, `acks=all` — иначе ретраи переставили бы сообщения и сломали равенство «отброшено = ожидаемые отбросы». При `--speed max` `produce()` повторяется после `poll()`, если локальная очередь переполнена (`BufferError`).
- `--duration` (секунды симуляции) — для e2e и записи датасетов. По окончании генератор досылает отложенные дубли, опоздания и обрывы в их порядке, пишет итог в stdout и `/out/summary.json` (`produced`, `faults{type}`, `expected_drops`, `decisions{received, applied, ignored{reason}}`) и завершается.

### 4.5 Сбои

Параметры: `--seed`, `--dup-rate` (по умолчанию 0,005), `--late-rate` (0,002), `--outage-rate` (0,0005 на машину за тик).

- **Дубль:** копия сообщения отправляется ещё раз через 0–60 с.
- **Опоздание:** сообщение задерживается на 2–60 с. Только на дороге — дальше 100 м от станций и разгрузки.
- **Обрыв связи:** машина копит сообщения 5–60 с, потом отправляет накопленное по порядку `ts`. Начинается, только если машина дальше 700 м от станций и разгрузки, чтобы обрыв закончился до подъезда.
- Порядок отправки на тике: текущие сообщения по `unit_uuid`, затем назначенные на этот тик дубли и опоздания, затем досылка обрывов. Сообщение тика, на котором обрыв кончается, входит в досылку последним.
- Ожидаемые отбросы: генератор применяет правило «`ts` не больше последнего — отбросить» к собственному порядку отправки и ведёт `expected_drops_total`. Сервис должен отбросить ровно столько же.

### 4.6 Метрики генератора

`vq_gen_telemetry_produced_total`, `vq_gen_faults_injected_total{type}`, `vq_gen_expected_drops_total`, `vq_gen_decisions_received_total`, `vq_gen_decisions_applied_total`, `vq_gen_decisions_ignored_total{reason}`, `vq_gen_decision_delay_sim_seconds`, `vq_gen_sim_time_seconds`.

## 5. Витрина

### 5.1 Живая страница `viewer`

FastAPI 0.142.1 + uvicorn 0.54.0, порт 8000.

- Фоновый поток Kafka: `queue.v1` с начала — по каждой станции хранится запись с наибольшим `vq-src-offset`; из `decision.v1` — последние 200 записей с дедупликацией по `(unit_uuid, at)`. После `make reset` (offset ушёл назад) кеш сбрасывается.
- Postgres, только чтение: `processor`, `stations`, `vehicles` одной транзакцией `REPEATABLE READ READ ONLY` — согласованный срез на `next_offset`. Postgres отстаёт от `queue.v1` не больше чем на пачку; страница показывает обе отметки («очереди на offset X, карта на offset Y»).
- У каждого источника свой таймаут (1 с); недоступный источник помечается на странице, остальное продолжает обновляться.
- `GET /api/state` — JSON:
  - «сейчас»;
  - станции: координаты, занявшая машина, очередь из `queue.v1`;
  - машины: позиция, фаза, цель, своя станция;
  - лента решений;
  - здоровье: `epoch`, `next_offset`, `updated_at` и точные счётчики из строки `processor` (принято, отброшено, невалидно); ожидаемые отбросы — из `/metrics` генератора (или `summary.json` после e2e); решения по типам и точность прогноза — из `/metrics` dispatcher.
- `GET /` — `static/index.html` на чистом JS и SVG:
  - карта: станции с кругами 50 м и 1500 м, разгрузка, машины цветом фазы, пунктир к цели у перенаправленных;
  - карточки очередей станций;
  - лента решений и полоса здоровья;
  - опрос `/api/state` раз в 500 мс.
- В `ARCHITECTURE.md` оговаривается, что чтение внутренних таблиц процессора — операторский вид для демо; в продакшене витрина читала бы опубликованные топики или реплику.

- `vq_station_releases_total{station, reason}`
- `vq_batch_seconds`, `vq_checkpoint_seconds` (гистограммы), `vq_consumer_lag_messages`, `vq_epoch`

Grafana: источник Prometheus и дашборд «Виртуальные очереди» подключаются через provisioning. Панели:
- поток сообщений и отбросы против ожидания генератора;
- решения по типам и выигрыш;

### 6.3 Сквозные

- `make e2e`: `make reset`; генератор `--speed 20 --duration 3600 --seed 42` (около 3 минут); ждём его выхода, берём high watermark `telemetry.v1`, ждём, пока `processor.next_offset` его догонит, затем `make verify`. Дополнительные проверки:
  - `processor.msgs_not_newer` = `summary.expected_drops`;
  - `summary.decisions.ignored{already_serving}` = 0 и `vq_fsm_resync_total` = 0;
  - есть и `recommended`, и `no_gain`;
  - по офлайн-прогону: на станции не больше одной занявшей, машина не больше чем в одной строке, каждая машина прошла хотя бы один цикл.

  Точные числа и хэши e2e не проверяет: телеметрия замкнутого контура зависит от часов старта и задержек решений.
- `make e2e-chaos`: то же, но в середине прогона дважды `docker compose kill -s KILL dispatcher` в случайные моменты. `verify` должен пройти и показать ≥ 1 повтор; измеренное время восстановления печатается и идёт в README.
- `make verify` (`tools/verify.py`, в образе приложения): берёт `N = processor.next_offset`; прогоняет `telemetry.v1[0, N)` через `Engine` офлайн с пустого состояния, помечая каждый выход его `src_offset`; читает `queue.v1` и `decision.v1` целиком и оставляет записи с `vq-src-offset < N`. Записи с одинаковыми `(топик, ключ, vq-src-offset)` — повторы: они обязаны совпадать байт в байт (иначе провал), считаются и схлопываются. После этого по каждому ключу последовательность в порядке `vq-src-offset` обязана совпасть с офлайн-последовательностью. `min.compaction.lag.ms` сутки гарантирует, что за прогон компакция ничего не удалит.

## 10. Известные ограничения и риски

- **Задержка на станции.** Если машина обслуживается дольше 230 с, станцию передают по таймеру, и прогноз для следующих оптимистичен. ТЗ требует освобождения по таймеру; это же защищает от потерянной телеметрии занявшей.
- **Часы машины спешат.** «Сейчас» уходит вперёд, остальные машины становятся несвежими. Защиты нет (буква ТЗ); нужен watermark или карантин будущих `ts`.
- **Холодный старт без состояния при непустом топике.** По букве ТЗ первая позиция трактуется как «к станции», и машина, едущая к разгрузке, считается неверно до разгрузки.
- **Пропущенный радиус разгрузки.** Если ни одна точка не попала в радиус 50 м разгрузки, машина остаётся «к разгрузке» (буква ТЗ). Генератор такого не создаёт.
- **Неисполненная рекомендация.** Если генератор не успел исполнить рекомендацию (машина уже начала обслуживание дома, долгий простой dispatcher), модель сходится через самолечение при остановке у фактической станции. До этого машина стоит строкой в очереди рекомендованной станции, и прогноз там пессимистичен. Видно в `vq_fsm_resync_total`.
- **Перезапуск генератора без сброса** не поддерживается: генератор отказывается стартовать на непустом топике (флаг `--allow-dirty` — на свой риск, модель сходится примерно за цикл).
- **Выигрыш считается по ожиданию, а не по времени начала обслуживания.** В примере T4 на S2 начнёт обслуживание на 70 с позже, чем на S1, но правило ТЗ рекомендует S2. Реализовано как в ТЗ, отмечено в README.
- **Выходы at-least-once.** После падения возможны повторы уже выданных записей, в том числе одинаковые очереди подряд; потребители схлопывают их по `vq-src-offset`.
- **Брокер — одна нода в dev-container без fsync.** Потеря ноды — потеря данных; гарантии предполагают кластер с RF=3.
- **Инкрементальности нет.** Все очереди пересчитываются на каждое сообщение; при ×10 машин на площадку это станет узким местом.
- **Одна площадка — одна партиция — одно ядро.** Масштабирование — по площадкам.
